Chapitre 07 · 60 min

Packages

En pratique, presque tout le code PL/SQL professionnel vit dans des packages. Un recruteur s'attend à ce que tu saches expliquer pourquoi, et à ce que tu en écrives un sans hésiter.

  • séparer spécification (contrat public) et corps (implémentation) ;
  • utiliser variables de package, section d'initialisation et surcharge ;
  • expliquer les avantages en dépendances, performance et sécurité ;
  • comprendre l'erreur ORA-04068 sur l'état de package.

Tout ce qui est déclaré dans la spécification est public. Tout ce qui n'est que dans le corps est privé.

Un package se crée en deux ordres distincts : d'abord la spécification (CREATE PACKAGE), qui déclare ce que les autres ont le droit d'utiliser, puis le corps (CREATE PACKAGE BODY), qui contient le code. La spécification compile sans le corps ; l'inverse est impossible. Les appelants ne voient que la spécification et s'écrivent pkg_rh.augmenter(…).

Les en-têtes des sous-programmes publics doivent être identiques dans la spécification et dans le corps (mêmes noms de paramètres, types et modes), sinon le corps ne compile pas (PLS-00323). Une procédure privée comme valider_salaire doit être définie avant d'être appelée dans le corps, ou annoncée plus haut par une déclaration anticipée (forward declaration).

Piège

Le troisième paramètre de la seconde version d'augmenter est un BOOLEAN. Avant 23ai, ce type n'existe pas en SQL : cette version n'est appelable que depuis du code PL/SQL. Un CALL SQL ne peut pas l'atteindre, et une application cliente passe par un bloc anonyme BEGIN pkg_rh.augmenter(20, 5, TRUE); END;. Depuis 23ai, BOOLEAN est aussi un type SQL. Autre danger de cette surcharge : pkg_rh.augmenter(20, 5) appelle la version à deux paramètres, donc augmente l'employé n°20, qui n'existe pas. Aucune erreur, zéro ligne modifiée. Dans du vrai code, un nom explicite (augmenter_dept) serait plus sûr.

pkg_rh initialisé Appels dans cette session : 2 SMIC : 1400 Refusé : ORA-20100: Salaire invalide : 900

L'exception publique e_regle_metier est associée au code -20100 par PRAGMA EXCEPTION_INIT : l'appelant l'intercepte par son nom (voir le chapitre 05). La première ligne n'apparaît que si c'est le premier appel de pkg_rh dans ta session. Relance le bloc : elle disparaît et le compteur affiche 5, car l'embauche refusée avait porté le compteur à 3 avant la validation du salaire, et le ROLLBACK ne l'a pas remis à zéro.

Pourquoi des packages ?

AvantageExplication
EncapsulationOn expose une API stable et on cache les détails (procédures privées, variables).
DépendancesLes appelants dépendent de la spécification. Recompiler le corps n'invalide pas les appelants, ce qui évite les cascades d'invalidation.
PerformanceAu premier appel, tout le package est chargé dans la mémoire partagée (shared pool) : les appels suivants à ses autres sous-programmes n'ont rien à recharger.
État de sessionLes variables de package conservent leur valeur entre les appels, pendant toute la session.
SurchargePlusieurs sous-programmes de même nom avec des paramètres différents (en nombre, ordre ou famille de types). Impossible pour des procédures autonomes.
SécuritéUn seul GRANT EXECUTE ON pkg_rh donne accès à toute l'API, sans accès direct aux tables.

L'état de package et la section d'initialisation

Les variables, constantes et curseurs déclarés au niveau du package (dans la spécification ou dans le corps, hors de tout sous-programme) forment son état. Chaque session a sa propre copie de cet état, en mémoire de session (UGA) : deux utilisateurs ne partagent jamais g_nb_appels. L'état est créé à la première référence au package dans la session (appel d'un sous-programme ou lecture d'une variable publique) : Oracle initialise les variables, puis exécute une fois la section d'initialisation. Il dure ensuite jusqu'à la fin de la session.

Piège

Une variable de package n'est pas partagée entre sessions et n'est pas transactionnelle : un ROLLBACK ne remet pas g_nb_appels à sa valeur précédente. Avec un pool de connexions côté application, une variable de package peut « fuiter » d'un utilisateur web à l'autre qui réutilise la même session : réinitialise-la explicitement, ou ne t'en sers pas pour des données propres à un utilisateur.

ORA-04068 : l'état a été jeté

Si un package a un état et qu'on recompile son corps (un déploiement, par exemple) pendant que des sessions l'ont déjà instancié, chacune de ces sessions reçoit une erreur à son prochain appel. Voici ce qu'affiche SQL*Plus en 19c pour un EXEC pkg_rh.augmenter(103, 5) (23ai formule les messages un peu différemment et ajoute un lien d'aide) :

ORA-04068: existing state of packages has been discarded ORA-04061: existing state of package body "RH.PKG_RH" has been invalidated ORA-04065: not executed, altered or dropped package body "RH.PKG_RH" ORA-06508: PL/SQL: could not find program unit being called: "RH.PKG_RH" ORA-06512: at line 1

(RH est ici le schéma propriétaire.) L'appel suivant fonctionne, car le package est instancié à nouveau, mais les valeurs des variables sont perdues. Les remèdes :

  • éviter les variables globales quand elles ne servent à rien : un package sans état n'a pas ce problème. Depuis 11.2.0.2, un package dont les seuls éléments d'état sont des constantes connues à la compilation (valeur littérale ou expression statique, comme c_smic) est traité comme sans état. Ce n'est pas le cas de pkg_rh, à cause de g_nb_appels ;
  • isoler l'état dans un petit package séparé, rarement modifié, et garder la logique dans un package sans état qu'on peut redéployer ;
  • côté application, intercepter ORA-04068 et relancer l'appel une fois ;
  • pour des déploiements sans interruption : l'Edition-Based Redefinition (11gR2).
En entretien

« Recompiler un corps de package n'invalide pas les appelants » et « recompiler un corps de package avec état provoque ORA-04068 dans les sessions qui l'utilisent » sont deux affirmations vraies en même temps. La première concerne les dépendances (statut VALID/INVALID des objets), la seconde l'état en mémoire des sessions. Savoir les distinguer fait bonne impression.

Astuce

La clause ACCESSIBLE BY (PACKAGE pkg_api) (12c) limite les unités autorisées à appeler un package : utile pour un package « interne » qui ne doit être appelé que par la couche API. Tout autre appel est refusé à la compilation (PLS-00904).

Packages fournis par Oracle

Oracle livre des centaines de packages DBMS_* et UTL_*. Ceux-ci reviennent souvent en entretien :

PackageUsage typique
DBMS_OUTPUTPUT_LINE écrit dans un tampon que le client (SQL*Plus, SQL Developer) affiche à la fin de l'appel. Outil de mise au point, pas de journalisation en production.
DBMS_UTILITYFORMAT_ERROR_BACKTRACE, FORMAT_CALL_STACK, GET_TIME (chronométrage en centièmes de seconde). Voir le chapitre 05.
DBMS_SESSIONRESET_PACKAGE (jette l'état de tous les packages de la session), SET_IDENTIFIER (identifier l'utilisateur applicatif).

Exercices

Exercice 1 · Package utilitaire de dates

facile

Crée pkg_dates avec une constante publique c_format ('DD/MM/YYYY'), une fonction jours_ouvres(p_debut DATE, p_fin DATE) qui compte les jours du lundi au vendredi entre deux dates incluses, et une fonction privée est_weekend(p_d DATE) RETURN BOOLEAN.

Voir la solution

TO_CHAR(d, 'D') dépend du paramètre NLS_TERRITORY (le 1er jour de la semaine n'est pas le même en France et aux États-Unis) : piège classique. L'écart avec TRUNC(d, 'IW') est fiable partout. La fonction privée renvoie un BOOLEAN : possible car elle n'est appelée que depuis PL/SQL. La fonction publique, elle, est appelée depuis SQL : elle renvoie un type numérique. Les jours fériés (le 11 novembre par exemple) ne sont pas gérés : il faudrait une table de jours fériés.

Exercice 2 · Compléter pkg_rh

moyen

Ajoute à pkg_rh une procédure publique licencier(p_emp_id) qui refuse (erreur -20101) de supprimer un employé qui manage encore quelqu'un, et une fonction publique masse_salariale(p_dept_id DEFAULT NULL) qui renvoie la masse d'un département, ou de toute l'entreprise si le paramètre est NULL. Pense à modifier la spécification et le corps.

Voir la solution

La contrainte de clé étrangère manager_id bloquerait de toute façon la suppression (ORA-02292), mais le contrôle explicite donne un message métier compréhensible. La suppression de l'historique avant celle de l'employé est nécessaire pour la même raison (clé étrangère de historique_salaires). Sans NVL, le département 40 renverrait NULL.

Exercice 3 · Cache de session

difficile

Crée pkg_cache_dept avec une fonction nom(p_dept_id) qui lit le nom du département en base au premier appel, puis le garde en mémoire (tableau associatif privé) pour les appels suivants de la session. Ajoute une procédure vider. Quel est le risque de ce cache comparé à RESULT_CACHE ?

Voir la solution

Risques : le cache est par session (chaque session le remplit, la mémoire de session, l'UGA, est multipliée par le nombre de sessions) et il n'est jamais invalidé si quelqu'un renomme un département. RESULT_CACHE est partagé entre sessions et invalidé automatiquement quand la table change.

Exercice 4 · Surcharger jours_ouvres

moyen

Ajoute à pkg_dates une seconde version de jours_ouvres qui accepte deux chaînes au format c_format, de sorte que pkg_dates.jours_ouvres('26/10/2026', '08/11/2026') renvoie aussi 10. Ne duplique pas la logique de calcul. Pourquoi cette surcharge est-elle autorisée ?

Voir la solution

Les deux versions ont le même nombre de paramètres, mais VARCHAR2 et DATE appartiennent à des familles de types différentes : Oracle choisit la version d'après le type des arguments. Avec une chaîne qui ne respecte pas le format, TO_DATE lève une erreur (par exemple ORA-01843 pour un mois invalide) : c'est voulu, une date mal formée ne doit pas donner un résultat silencieux.

Quiz

Questions d'entretien

Peut-on avoir une spécification sans corps ?

Oui, si elle ne déclare que des éléments sans implémentation : constantes, types, exceptions, variables. C'est courant pour un package de constantes ou de types partagés. Le corps devient obligatoire dès qu'on déclare un sous-programme ou un curseur avec requête cachée.

Si je modifie le corps d'un package, les procédures qui l'appellent deviennent-elles invalides ?

Non. Elles dépendent de la spécification, pas du corps. Seule une modification de la spécification peut invalider les appelants, et depuis 11g le suivi fin des dépendances (fine-grained dependency tracking) les épargne si les éléments qu'ils utilisent n'ont pas changé, par exemple quand on ajoute un nouveau sous-programme à la spécification. C'est un des principaux arguments en faveur des packages.

Quelles sont les règles de la surcharge ?

Les versions doivent différer par le nombre, l'ordre ou la famille de types des paramètres. Différer uniquement par le mode (IN/OUT), par le type de retour, ou par des sous-types de la même famille (NUMBER / INTEGER) rend l'appel ambigu : PLS-00307: too many declarations of 'X' match this call. Si seuls les noms des paramètres diffèrent, l'appel positionnel est ambigu mais la notation nommée (p(x => 1)) permet de choisir. On peut surcharger des sous-programmes de package ou locaux, pas des procédures autonomes.

Qu'est-ce que SERIALLY_REUSABLE ?

Un PRAGMA qui limite la durée de vie de l'état d'un package à un seul appel serveur au lieu de toute la session. Il économise de la mémoire dans les systèmes avec beaucoup de sessions, mais le package ne peut alors pas être utilisé depuis un trigger ni depuis une fonction appelée par une requête SQL.

Après un déploiement, des utilisateurs reçoivent ORA-04068 une fois, puis tout refonctionne. Que s'est-il passé ?

Le corps d'un package avec état (variables globales) a été recompilé alors que leurs sessions l'avaient déjà instancié. Oracle jette l'état de ces sessions : le premier appel échoue, le suivant réinstancie le package et fonctionne, mais les valeurs des variables sont perdues. Pour l'éviter : packages sans état, état isolé dans un package séparé, relance automatique côté application, ou Edition-Based Redefinition.
