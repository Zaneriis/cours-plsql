Chapitre 12 · 50 min

Bonnes pratiques et optimisation

La partie qui fait passer de « je sais écrire du PL/SQL » à « je sais livrer du PL/SQL en production ». En entretien, ces sujets sortent souvent sous la forme « raconte-moi comment tu as diagnostiqué un traitement lent ».

  • instrumenter un traitement pour le suivre en production ;
  • appliquer une démarche de diagnostic de performance ;
  • citer des conventions de code et les nouveautés récentes d'Oracle.

Instrumenter son code

DBMS_OUTPUT ne sert qu'en développement : rien ne s'affiche avant la fin du bloc et personne ne le lit en production. Les vrais outils :

  • Table de log alimentée par une procédure autonome (niveau, message, horodatage, FORMAT_ERROR_BACKTRACE). Le framework open source Logger en est un exemple répandu.
  • DBMS_SESSION.SET_IDENTIFIER pour retrouver l'utilisateur métier derrière un pool de connexions.
  • UTL_CALL_STACK (12c) pour connaître le sous-programme appelant, par exemple pour enrichir les logs.

Laisser le compilateur t'aider

D'autres avertissements utiles : PLW-06002 (code inaccessible), PLW-07204 (conversion qui empêche un index). La compilation native (PLSQL_CODE_TYPE = NATIVE) accélère le code très calculatoire, pas le code qui fait surtout du SQL.

Diagnostiquer un traitement lent

flowchart TD
  A["Traitement lent"] --> B{"Où passe le temps ?
DBMS_HPROF, AWR/ASH,
logs horodatés"}
  B -- "dans une requête SQL" --> C["Plan d'exécution :
DBMS_XPLAN.DISPLAY_CURSOR
index ? statistiques ? cardinalités ?"]
  B -- "dans le code PL/SQL" --> D{"Boucle ligne par ligne
avec SQL dedans ?"}
  D -- oui --> E["SQL ensembliste
ou BULK COLLECT + FORALL"]
  D -- non --> F["Fonction appelée en SQL ?
RESULT_CACHE, DETERMINISTIC,
ou réécriture en SQL"]
  B -- "en attente (verrous)" --> G["V$SESSION.BLOCKING_SESSION
transactions trop longues ?"]

Compare les colonnes E-Rows (estimé) et A-Rows (réel) : un gros écart signale des statistiques absentes ou fausses (DBMS_STATS.GATHER_TABLE_STATS). Pour le PL/SQL, le profileur hiérarchique DBMS_HPROF donne le temps passé par sous-programme.

Check-list performance à citer
  • Une requête ensembliste plutôt qu'une boucle.
  • BULK COLLECT … LIMIT et FORALL quand la boucle est nécessaire.
  • Variables liées en SQL dynamique.
  • Pas de fonction sur une colonne indexée dans le WHERE (sinon index sur fonction).
  • Pas de conversion implicite sur une colonne indexée.
  • COMMIT à la fin de l'unité de travail, pas à chaque ligne (chaque commit force une écriture du journal redo).
  • PLS_INTEGER pour les compteurs, cache de résultats pour les lectures répétées.

Pourquoi préfixer ?

Sans préfixe, une variable qui porte le nom d'une colonne est masquée par la colonne dans un ordre SQL. DELETE FROM employes WHERE nom = nom; avec une variable nom compare la colonne à elle-même… et supprime toute la table (sauf les noms NULL).

  • Un sous-programme fait une chose, tient sur un écran, et a un nom en verbe (calculer_prime).
  • Pas de valeurs en dur : constantes de package ou table de paramètres.
  • Tests unitaires avec utPLSQL, code versionné dans Git, déploiement scripté (Liquibase, Flyway, SQLcl project).

Exercices

Exercice 1 · Revue de code

moyen

Liste tous les problèmes de ce code (au moins 7) et propose une version corrigée.

Voir la solution
  1. Nom de procédure et de paramètre non explicites, pas de préfixe p_.
  2. Variable salaire du même nom que la colonne : ambiguïté, dans l'UPDATE c'est la colonne qui est utilisée.
  3. Le curseur lit toute la table puis filtre en PL/SQL au lieu de filtrer dans le WHERE.
  4. Le SELECT INTO relit une ligne déjà lue par le curseur : inutile.
  5. Un UPDATE par ligne au lieu d'un seul ordre ensembliste.
  6. COMMIT dans la boucle : lent, et le traitement ne peut plus être annulé en cas d'erreur.
  7. WHEN OTHERS THEN NULL : erreurs avalées silencieusement.
  8. Pas de type ancré (%TYPE), pas de compte rendu du nombre de lignes, pas de taux en paramètre.

Exercice 2 · Instrumenter un batch

moyen

Crée un package pkg_log avec info(p_msg) et erreur(p_msg) qui écrivent dans une table journal (à créer : id, horodatage, niveau, programme, message) en transaction autonome. Le nom du programme appelant doit être trouvé automatiquement avec UTL_CALL_STACK.

Voir la solution

Le calcul de l'appelant se fait dans info / erreur (profondeur 3 depuis appelant) avant d'entrer dans ecrire, pour que la profondeur soit stable.

Questions d'entretien

Comment as-tu déjà optimisé un traitement PL/SQL ?

Structure ta réponse : mesure (logs horodatés, DBMS_HPROF, AWR), cause (ex. boucle de 2 millions d'UPDATE unitaires avec COMMIT à chaque ligne), action (réécriture en MERGE ensembliste ou BULK COLLECT + FORALL, commit en fin de lot), résultat chiffré (« de 3 h à 6 min »). Un exemple concret vaut mieux qu'une liste théorique.

Comment tester du code PL/SQL ?

Avec un framework de tests unitaires comme utPLSQL (annotations --%suite, --%test, assertions ut.expect), en isolant les données de test et en annulant les modifications après chaque test. Les tests tournent en intégration continue avec le déploiement des scripts.
