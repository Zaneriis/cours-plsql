Spécial entretien

Tout ce qui se révise en dernière ligne droite : des cartes questions-réponses sur tout le programme, les requêtes SQL qu'on te demandera presque sûrement d'écrire, les pièges des tests de lecture de code et deux cas pratiques chronométrés.

  • répondre en une ou deux phrases claires aux questions théoriques classiques ;
  • écrire sans hésiter les requêtes SQL d'entretien, en pensant aux NULL ;
  • repérer les bugs d'un code PL/SQL en 20 minutes ;
  • réaliser un package complet en 45 minutes ;
  • préparer tes propres questions au recruteur.

Flashcards

Lis la question, réponds à voix haute, puis retourne la carte. Classe-la « Je sais » ou « À revoir » : le filtre te permet de ne retravailler que les cartes difficiles. Ton classement est enregistré. Les cartes couvrent tous les chapitres, de l'architecture au SQL d'entretien.

Le SQL qu'on te demandera aussi

Un poste PL/SQL est d'abord un poste SQL. Ces requêtes reviennent dans la grande majorité des entretiens. Les sorties correspondent au schéma d'exemple du chapitre 00.

SQL 1 · Le deuxième salaire le plus élevé

classique

Écris la requête qui renvoie le deuxième salaire le plus élevé de l'entreprise, puis généralise au N-ième.

Voir la solution
7200
Deux pièges dans la même question

En ORDER BY … DESC, Oracle place les NULL en premier (ils sont considérés comme plus grands que tout). Sans NULLS LAST ou WHERE salaire IS NOT NULL, un seul salaire inconnu décale le classement. Dans la version 12c, le DISTINCT est indispensable : avec deux salaires ex aequo au sommet, OFFSET 1 renverrait encore le maximum.

SQL 2 · Le mieux payé de chaque département

classique

Affiche, pour chaque département, l'employé (ou les employés ex aequo) au salaire le plus élevé.

Voir la solution
10 Martin 9500 20 Bernard 7200 30 Moreau 6800

Différence à connaître : ROW_NUMBER (1, 2, 3 même en cas d'égalité), RANK (1, 1, 3), DENSE_RANK (1, 1, 2). Ici RANK garde les ex aequo ; ROW_NUMBER en choisirait un arbitrairement. Version sans analytique : WHERE (dept_id, salaire) IN (SELECT dept_id, MAX(salaire) FROM employes GROUP BY dept_id).

SQL 3 · Supprimer les doublons

classique

Une table contacts(id, email) contient des emails en double. Garde la ligne au plus petit id pour chaque email.

Voir la solution

Les deux versions ne traitent pas les emails NULL de la même façon : PARTITION BY regroupe les NULL ensemble (ils sont dédoublonnés), alors que c2.email = c.email n'est jamais vrai pour NULL (ils sont tous conservés). Pense aussi à demander si Jean@x.fr et jean@x.fr sont des doublons : il faudrait alors partitionner sur LOWER(TRIM(email)). Commence par un SELECT avec la même condition avant de lancer le DELETE.

classique

a) Liste les départements sans employé. b) Affiche l'organigramme indenté à partir de la DG, les collègues d'un même manager triés par nom.

Voir la solution

PRIOR désigne la ligne parente : « le manager de l'enfant est l'emp_id du parent ». Un simple ORDER BY casserait l'arbre ; ORDER SIBLINGS BY trie seulement les frères. Bonus à citer : SYS_CONNECT_BY_PATH, CONNECT_BY_ISLEAF, et la version standard en WITH récursif (11g R2).

Pour chaque employé : son département, son salaire, la moyenne de son département, l'écart à cette moyenne et le cumul des salaires par ordre d'embauche dans le département.

Les fonctions analytiques gardent toutes les lignes, contrairement à GROUP BY. Piège : avec ORDER BY dans le OVER, la fenêtre par défaut est RANGE UNBOUNDED PRECEDING ; deux embauches le même jour reçoivent le même cumul. Pour un cumul strictement ligne à ligne, ajoute ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW et un critère de tri unique (date_embauche, emp_id). Question fréquente : « différence entre WHERE et HAVING » (filtre avant / après agrégation).

Les trois erreurs qu'on attend

Une jointure interne fait disparaître RH. COUNT(*) affiche 1 pour RH, car la jointure externe produit une ligne complétée par des NULL. Enfin, ajouter un filtre sur employes dans le WHERE (par exemple WHERE e.salaire > 3000) élimine ces lignes NULL et retransforme la jointure en jointure interne : le filtre doit aller dans le ON.

Cas pratique 1 : revue de code (20 minutes)

Format très courant : on te tend un code « qui ne marche pas » et on te demande ce qu'il fait vraiment, puis de le corriger. Lis-le à voix haute avant de répondre.

Trouve les bugs de prime_fin_annee

entretien

Cette procédure doit ajouter à la commission de chaque employé d'un département une prime de 10 % de son salaire, puis afficher le nom du département. Appelée avec 30, elle n'affiche rien et ne modifie rien. Explique pourquoi, liste tous les défauts (il y en a au moins six) et propose une version corrigée.

Voir la solution

Pourquoi rien ne se passe : dans un ordre SQL, la colonne dept_id masque le paramètre de même nom. WHERE dept_id = dept_id compare la colonne à elle-même : le SELECT INTO trouve les 4 départements et lève TOO_MANY_ROWS, que WHEN OTHERS THEN NULL avale. La procédure « réussit » sans rien faire.

  1. Paramètre nommé comme une colonne : le curseur aussi lit les 10 employés au lieu de ceux du département. Préfixer : p_dept_id (chapitre 12).
  2. WHEN OTHERS THEN NULL : masque toutes les erreurs. Traiter seulement NO_DATA_FOUND (département inexistant) et laisser remonter le reste (chapitre 05).
  3. EXIT WHEN en fin de boucle : après le dernier FETCH qui échoue, l_emp garde la ligne précédente, traitée une seconde fois. Ici l'effet est invisible (même calcul), mais un compteur ou un INSERT serait doublé (chapitre 04).
  4. Commission NULL : salaire * 0.1 + NULL vaut NULL, la prime des employés sans commission est perdue. Utiliser NVL(commission, 0) (chapitre 02).
  5. COMMIT dans la boucle : lent, valide un travail partiel en cas d'erreur, expose à ORA-01555 (fetch across commit) et retire la décision à l'appelant (chapitre 11).
  6. Ligne à ligne : un curseur et un UPDATE par employé là où un seul UPDATE suffit (chapitre 09).
  7. Bonus : le paramètre n'est pas ancré (employes.dept_id%TYPE) et le message ne dit pas combien d'employés ont été traités.
4 prime(s) versée(s) : Ventes

Pas de COMMIT : l'appelant valide. Avec 40, la procédure affiche 0 prime(s) versée(s) : RH ; avec 99, elle lève ORA-20010.

Cas pratique 2 : un package complet (45 minutes)

Gestion des augmentations annuelles

entretien

Écris un package pkg_augmentations avec une procédure publique appliquer(p_annee IN PLS_INTEGER, p_nb_ok OUT PLS_INTEGER, p_nb_ko OUT PLS_INTEGER) :

  1. Taux : 3 % pour les employés qui ont 5 ans d'ancienneté ou plus au 31 décembre de p_annee, 2 % sinon, 0 % pour les stagiaires.
  2. Une augmentation ne peut pas faire dépasser 10 000 : l'employé est alors plafonné à 10 000.
  3. Chaque modification est tracée dans historique_salaires.
  4. Un employé en erreur ne doit pas bloquer les autres : l'erreur est journalisée (transaction autonome) et comptée.
  5. Le traitement doit être performant pour 1 million d'employés.
  6. Pas de COMMIT de la transaction principale dans le package : l'appelant décide.

Avant d'ouvrir la solution : écris la spécification, puis le corps. Pose-toi les questions de cas limites : ancienneté pile à 5 ans, salaire déjà au-dessus du plafond, salaire NULL. Réfléchis à l'option SQL pur et à l'option FORALL … SAVE EXCEPTIONS.

Voir une solution
9 augmentés, 0 en erreur

Sur le schéma d'exemple, en 2026, la limite est le 01/01/2022 : Laurent (embauché en 2022) et Michel (2023) ont moins de 5 ans au 31/12/2026, Garcia est stagiaire.

Points à commenter devant le recruteur :

  • Ancienneté : « 5 ans au 31/12/2026 » équivaut à « embauché au plus tard le 31/12/2021 ». Comparer à date_embauche < 01/01/2022 règle à la fois le cas « pile 5 ans » et une éventuelle heure dans la date, et reste compatible avec un index, contrairement à un calcul MONTHS_BETWEEN appliqué à la colonne.
  • Plafond : LEAST(10000, …) seul ferait baisser un salaire déjà supérieur à 10 000. Le filtre salaire < c_plafond écarte ces employés (et les salaires NULL) : ils n'ont rien à recevoir.
  • Les stagiaires (0 %) sont exclus dès la requête : inutile de les mettre à jour ni de les tracer.
  • Le calcul est fait en SQL dans le curseur, les écritures en FORALL par lots de 1 000 : mémoire bornée, peu de changements de contexte.
  • SAVE EXCEPTIONS isole les lignes en erreur. ERROR_INDEX est la position dans le FORALL : comme il parcourt 1 .. COUNT, c'est aussi l'indice dans l_ids. ERROR_CODE est positif, d'où le -p_code pour SQLERRM.
  • INDICES OF l_ids parce que l_ids devient creuse ; FORALL i IN 1 .. l_ids.COUNT lèverait ORA-22160. l_anc et l_nouv restent denses : on les lit avec les indices encore présents dans l_ids, qui correspondent toujours à la même ligne. Le FETCH suivant réinitialise les trois collections.
  • Le journal est en transaction autonome : son COMMIT ne valide que le journal, qui survit à un éventuel ROLLBACK de l'appelant. SQLERRM ne peut pas être appelé dans un ordre SQL : on passe par une variable.
  • Interactions avec le chapitre 10 : si le trigger trg_employes_audit_sal existe, l'insertion dans l'historique ferait doublon ; il faut choisir l'un ou l'autre. Si trg_sal_plafond rejette une ligne, elle arrive dans SQL%BULK_EXCEPTIONS avec le code 20300, mais SQLERRM(-20300) ne restitue pas le message personnalisé du trigger.
  • Limites assumées : un employé supprimé par une autre session entre la lecture et l'UPDATE est compté « ok » alors que rien n'a été modifié (on pourrait vérifier SQL%BULK_ROWCOUNT(i)) ; pour se protéger des modifications concurrentes, on ajouterait FOR UPDATE au curseur, au prix d'un verrou sur toutes les lignes ciblées.
  • Alternative SQL pur, sans gestion fine des erreurs : un INSERT … SELECT dans l'historique puis un seul UPDATE avec la même expression, ou un UPDATE avec la clause LOG ERRORS INTO (table créée par DBMS_ERRLOG.CREATE_ERROR_LOG), qui joue en SQL un rôle proche de SAVE EXCEPTIONS. Sur un million de lignes, c'est souvent la solution la plus rapide : dis-le.

Les questions à poser au recruteur

En fin d'entretien, « Avez-vous des questions ? » n'est pas une formalité : de bonnes questions montrent que tu sais à quoi ressemble un vrai projet PL/SQL, et les réponses t'apprennent beaucoup sur le poste.

QuestionCe que la réponse t'apprend
Quelle version d'Oracle utilisez-vous ? Une migration est-elle prévue ?Si tu pourras utiliser les nouveautés (12c, 19c, 23ai) ou si tu maintiendras du 11g.
Quelle part du métier est en PL/SQL, et quelle part dans l'application (Java, .NET…) ?Si le PL/SQL est le cœur du système ou une couche de procédures appelées par l'application.
Comment le code est-il versionné, testé et déployé ?Git, revue de code, tests utPLSQL, intégration continue, outils de déploiement (Liquibase, Flyway) : le niveau de maturité de l'équipe.
Quels volumes traitez-vous, et y a-t-il des traitements de nuit ?Si la performance (BULK, parallélisme, partitionnement) sera ton quotidien.
Qui s'occupe des DBA, des plans d'exécution, de la production ?Ton périmètre réel, et l'existence d'astreintes.
À quoi ressemblerait mon premier mois ?L'accompagnement prévu pour un profil débutant confirmé.
