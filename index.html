    Une base Oracle récente est une base conteneur (CDB, ici FREE) qui héberge des bases enfichables (PDB, ici FREEPDB1). Si tu te connectes au service FREE ou au SID FREE, tu arrives dans le conteneur racine : l'utilisateur rh n'y existe pas (ORA-01017: invalid username/password), et un CREATE USER rh lancé là en system échoue avec ORA-65096 (nom d'utilisateur commun invalide).     Quiz

    Questions d'entretien

    Pourquoi travailler avec un utilisateur dédié plutôt que SYSTEM ?

    Par moindre privilège : SYSTEM a le rôle DBA, donc une erreur de manipulation peut toucher toute la base, et un code qui fonctionne sous SYSTEM peut échouer en production faute de privilèges. Par isolation : un schéma applicatif regroupe ses propres objets, qu'on peut exporter, supprimer ou recréer sans toucher aux objets internes d'Oracle. Enfin, les comptes d'administration sont réservés à l'administration : Oracle déconseille d'y créer des objets applicatifs.

    Quelle différence entre une CDB et une PDB ?

    Depuis la 12c, une base conteneur (CDB) héberge une ou plusieurs bases enfichables (PDB). Chaque PDB a ses propres utilisateurs, schémas et données applicatives ; le conteneur racine (CDB$ROOT) porte le dictionnaire commun et les utilisateurs communs (préfixés C##). Les applications se connectent à une PDB par son nom de service. Depuis la 21c, l'architecture multitenant est la seule possible.

    Comment retrouver rapidement la structure d'une table ou la liste de tes objets ?

    DESC table dans l'outil client pour les colonnes ; sinon le dictionnaire : USER_TAB_COLUMNS pour les colonnes, USER_OBJECTS pour tous les objets avec leur type et leur statut (VALID/INVALID), USER_CONSTRAINTS pour les contraintes, USER_SOURCE pour le code PL/SQL stocké. Penser aux noms en majuscules dans les filtres.

    Chapitre 01 · 60 min

    Architecture et bloc PL/SQL

    PL/SQL est le langage procédural d'Oracle : il ajoute variables, boucles, conditions et gestion d'erreurs autour du SQL, et il s'exécute dans le serveur de base de données, au plus près des données. En entretien, les premières questions portent presque toujours sur ce socle : comment le code s'exécute, comment il est compilé, et ce qui se passe quand il casse.

    • expliquer ce qui se passe entre le moteur PL/SQL et le moteur SQL ;
    • écrire un bloc avec ses sections, des blocs imbriqués et des étiquettes ;
    • distinguer bloc anonyme et unités stockées, lire une erreur de compilation ;
    • distinguer une erreur PLS- d'une erreur ORA- et expliquer ORA-06550 ;
    • expliquer les dépendances, l'état INVALID et la recompilation ;
    • connaître le fonctionnement et les limites de DBMS_OUTPUT.

    Deux moteurs dans le serveur

    Quand tu envoies un bloc PL/SQL, le serveur Oracle le confie au moteur PL/SQL. Celui-ci exécute lui-même les instructions procédurales (affectations, IF, boucles) et passe chaque ordre SQL au moteur SQL. Chaque passage d'un moteur à l'autre est un changement de contexte : il a un coût. Toute la partie « performance » du cours (chapitre 09) consiste à en réduire le nombre.

    Un seul aller-retour réseau pour tout le bloc, mais un changement de contexte à chaque ordre SQL.

    Le SQL écrit directement dans le code (SQL statique) est vérifié dès la compilation : si une colonne n'existe pas, le bloc ne compile pas. Pour l'essentiel, seuls les ordres DML (SELECT … INTO, INSERT, UPDATE, DELETE, MERGE) et de contrôle de transaction (COMMIT, ROLLBACK, SAVEPOINT) s'écrivent tels quels. Le détail du SQL dans PL/SQL est au chapitre 04.

    Piège : ce que le moteur PL/SQL refuse
    • Un SELECT sans INTO (ni curseur) : PLS-00428: an INTO clause is expected in this SELECT statement. Un bloc PL/SQL n'affiche pas de résultat de requête tout seul.
    • Un ordre DDL (CREATE TABLE, TRUNCATE, ALTER…) écrit tel quel : erreur de syntaxe PLS-00103. Il faut passer par EXECUTE IMMEDIATE (chapitre 11).
    En entretien : « Pourquoi utiliser PL/SQL plutôt que tout faire côté application ? »
    • Performance : un seul appel réseau au lieu de dizaines, et le code tourne à côté des données.
    • Sécurité : on donne EXECUTE sur une procédure sans donner l'accès direct aux tables.
    • Réutilisation et cohérence : la règle métier est écrite une fois, quel que soit le client (Java, Python, batch).
    • Intégration SQL : types identiques à ceux des colonnes, SQL statique vérifié à la compilation, dépendances suivies par Oracle.

    Sois nuancé : une logique purement applicative (appel d'API, rendu) n'a rien à faire en base, et le code PL/SQL se déploie et se teste différemment du code applicatif.

    Anatomie d'un bloc

    Tout code PL/SQL est organisé en blocs. Seule la section BEGIN … END est obligatoire, et elle doit contenir au moins une instruction (NULL; fait l'affaire).

    Quelques règles de syntaxe à avoir en tête :

    • chaque instruction et chaque déclaration se termine par ;, y compris END; ;
    • l'affectation s'écrit := ; le signe = est la comparaison ;
    • le / seul sur sa ligne n'est pas du PL/SQL : c'est l'ordre donné à SQL*Plus ou SQL Developer (mode script) d'envoyer le bloc au serveur ;

    • les types, %TYPE et la gestion de NULL sont détaillés au chapitre 02, la section EXCEPTION au chapitre 05.

    Blocs imbriqués et portée

    Un bloc peut contenir d'autres blocs, dans sa section exécutable ou dans sa section d'exception. Une variable est visible dans le bloc qui la déclare et dans ses sous-blocs, et elle disparaît au END de son bloc. Si un sous-bloc redéclare le même nom, il masque la variable externe ; on peut encore l'atteindre en étiquetant le bloc externe avec <<nom>> et en qualifiant la variable (externe.l_x). L'étiquette peut être répétée après le END pour la lisibilité.

    Piège

    Référencer une variable hors de sa portée (ici l_y après le sous-bloc) n'est pas une erreur d'exécution mais une erreur de compilation : PLS-00201: identifier 'L_Y' must be declared. Tout le bloc est alors rejeté, y compris les lignes qui précèdent.

    Compilation : PLS- ou ORA- ?

    Avant de s'exécuter, tout code PL/SQL est compilé. Le compilateur vérifie la syntaxe, puis résout chaque nom (variables, tables, colonnes, procédures appelées) et vérifie les types et les droits. Il produit alors un code exécutable : du m-code interprété par défaut, ou du code machine si PLSQL_CODE_TYPE = NATIVE. Pour une unité stockée, le résultat est enregistré dans le dictionnaire ; pour un bloc anonyme, il est utilisé immédiatement.

    Dépendances et invalidation

    Oracle enregistre les dépendances de chaque unité stockée : une procédure qui lit employes et appelle nom_departement dépend de ces deux objets. Quand un objet référencé change, ses dépendants peuvent passer à l'état INVALID. Il n'y a rien à faire dans l'immédiat : au prochain appel, Oracle tente une recompilation automatique. Si elle réussit, l'appel se déroule normalement ; sinon l'appelant reçoit une erreur (comme PLS-00905 ci-dessus).

    flowchart LR

    (ALTER TABLE, nouvelle spécification…)" --> I["INVALID"]
  I -- "appel suivant ou
    ALTER … COMPILE" --> R{"Recompilation"}
  R -- "succès" --> V

    Le cycle de vie d'une unité stockée face aux modifications de ce dont elle dépend.

    • Depuis 11g, les dépendances sont suivies finement (au niveau des éléments utilisés) : ajouter une colonne à employes n'invalide pas une procédure qui ne cite que nom et salaire. Une unité qui utilise employes%ROWTYPE ou SELECT * dépend de la structure complète : elle est invalidée, comme une unité qui fait un INSERT sans liste de colonnes. La recompilation automatique au prochain appel la remet en général d'aplomb.
    • Supprimer ou modifier une colonne utilisée, ou changer la signature d'une procédure appelée, invalide les dépendants. Si la colonne a disparu, la recompilation échoue.
    • Les appelants d'un package ne dépendent que de sa spécification : recompiler le corps ne les invalide pas (chapitre 07).

    Après un déploiement, une bonne pratique consiste à vérifier qu'il ne reste aucun objet INVALID (SELECT … FROM user_objects WHERE status = 'INVALID') plutôt que de compter sur la recompilation automatique : elle déplace l'erreur vers le premier utilisateur qui appelle le code, en production.

    Quiz

    Questions d'entretien

    Quelle est la différence entre SQL et PL/SQL ?

    SQL est un langage déclaratif : on décrit le résultat voulu, une instruction à la fois. PL/SQL est un langage procédural qui encapsule du SQL dans des blocs avec variables, conditions, boucles et exceptions. PL/SQL est exécuté par le moteur PL/SQL du serveur ; le SQL qu'il contient est délégué au moteur SQL. Chaque passage de l'un à l'autre est un changement de contexte, d'où l'intérêt de traiter les données par lots (BULK COLLECT, FORALL, chapitre 09) ou, mieux, en un seul ordre SQL quand c'est possible.

    Qu'est-ce qu'un bloc anonyme ? Quand l'utiliser ?

    Un bloc sans nom, non stocké dans le dictionnaire, compilé à chaque envoi. On l'utilise pour des scripts ponctuels (migration de données, test, administration). Pour du code appelé régulièrement ou partagé, on crée une procédure, une fonction ou mieux un package : compilé une fois, protégé par des droits (GRANT EXECUTE), suivi par les dépendances.

    Quelle différence entre une erreur PLS- et une erreur ORA- ? Que signifie ORA-06550 ?

    Une erreur PLS- est une erreur de compilation PL/SQL (syntaxe, identifiant inconnu, mauvais arguments) : le code ne s'exécute pas et aucune section EXCEPTION ne peut l'intercepter. Une erreur ORA- vient du serveur, le plus souvent à l'exécution (aucune ligne, trop de lignes, valeur invalide), et peut être traitée dans EXCEPTION. ORA-06550 signale qu'un bloc anonyme n'a pas compilé : elle indique la ligne et la colonne, et est suivie de l'erreur PLS- réelle. Exception notable : une erreur SQL détectée à la compilation, comme PL/SQL: ORA-00942, porte le préfixe ORA-.

    Que se passe-t-il quand on modifie une table utilisée par une procédure ?

    Selon la modification, la procédure peut passer à l'état INVALID. Depuis 11g, le suivi fin des dépendances évite les invalidations inutiles (ajouter une colonne non utilisée, par exemple). Oracle recompile automatiquement l'unité au prochain appel ; si la recompilation échoue (colonne supprimée), l'appel lève une erreur, par exemple PLS-00905: object … is invalid. On vérifie avec USER_OBJECTS.STATUS, on lit les erreurs dans USER_ERRORS et on recompile avec ALTER PROCEDURE … COMPILE ou DBMS_UTILITY.COMPILE_SCHEMA. Pour limiter les cascades, on passe par des packages : les appelants ne dépendent que de la spécification.

    Pourquoi ne pas utiliser DBMS_OUTPUT pour tracer un traitement en production ?

    Parce que DBMS_OUTPUT écrit dans un tampon en mémoire de la session, que seul un client qui le demande lit, et seulement à la fin de l'appel. Une application Java ne le lit pas : les traces sont perdues. Le tampon peut être limité (20 000 octets avec DBMS_OUTPUT.ENABLE sans argument, ORU-10027), rien n'est visible pendant un long traitement, et rien n'est conservé une fois la session terminée. En production, on écrit dans une table de log via une transaction autonome (chapitre 05, chapitre 12) et on suit l'avancement avec DBMS_APPLICATION_INFO.

    Chapitre 02 · 60 min

    Variables, types et NULL

    Bien typer ses variables évite la moitié des bugs PL/SQL. La moitié restante vient souvent de NULL, qui ne se comporte comme aucune autre valeur. En entretien, ces deux sujets servent à vérifier très vite si tu as vraiment écrit du PL/SQL.

    • choisir le bon type scalaire et connaître ses limites (précision, longueur, plage) ;
    • déclarer par ancrage avec %TYPE / %ROWTYPE, nommer une règle avec SUBTYPE ;
    • calculer avec des DATE et des TIMESTAMP sans surprise ;
    • prévoir le résultat d'une expression qui contient NULL ;
    • éviter les conversions implicites dangereuses.

    Déclarer une variable

    Une déclaration par ligne : nom type [NOT NULL] [:= valeur | DEFAULT valeur];. Une variable sans valeur initiale vaut NULL, quel que soit son type (y compris NUMBER et PLS_INTEGER : il n'y a pas de 0 par défaut).

    Piège

    l_a, l_b NUMBER; ne compile pas (PLS-00103) : contrairement au C ou à Java, chaque variable a sa propre déclaration. Et une variable NOT NULL ou une constante sans valeur initiale est refusée à la compilation (PLS-00218 et PLS-00322).

    Dates : DATE, TIMESTAMP et arithmétique

    Une DATE contient toujours une heure (minuit si on ne l'a pas précisée). L'arithmétique se fait en jours : d + 1 est le lendemain, d + 1/24 une heure plus tard, et d2 - d1 renvoie un NUMBER de jours, avec des décimales si les heures diffèrent. Entre deux TIMESTAMP, la différence est un INTERVAL DAY TO SECOND.

    Jours écoulés : 122 Plus 36 heures : 02/09/2024 12:00 Mois écoulés : 4 Fin 6 mois : 28/02/2025 31/01 + 1 mois : 29/02/2024 Durée : 1 j 1 h 30 min

    Pour exploiter un INTERVAL, extrais ses composantes avec EXTRACT(DAY | HOUR | MINUTE | SECOND FROM …) : tu obtiens des nombres, indépendants du format d'affichage. Affiché tel quel, un INTERVAL DAY TO SECOND donne une chaîne du type +01 01:30:15, dont le nombre de chiffres dépend de la précision.

    BOOLEAN : avant et après 23ai

    Une condition est une expression BOOLEAN : on peut l'affecter directement (l_cadre := l_sal > 5000;), sans IF. Jusqu'à 21c, BOOLEAN n'existe qu'en PL/SQL : pas de colonne BOOLEAN, et une fonction qui prend ou renvoie un BOOLEAN ne peut pas être appelée depuis un SELECT (on renvoie alors 'O'/'N' ou 1/0, voir chapitre 06). Oracle 23ai ajoute BOOLEAN comme type SQL : colonnes BOOLEAN, TRUE et FALSE utilisables dans les requêtes, fonctions BOOLEAN appelables depuis SQL.

    cadre : non prime : inconnu

    Un BOOLEAN a trois états. CASE WHEN b THEN … ELSE 'non' END afficherait « non » pour NULL : d'où la branche WHEN NOT b explicite.

    Conversions

    Oracle convertit implicitement les types quand il le peut, en s'appuyant sur les paramètres de session (NLS_DATE_FORMAT, NLS_NUMERIC_CHARACTERS, NLS_DATE_LANGUAGE). Un code qui marche sur ton poste peut donc échouer, ou donner un autre résultat, sur le serveur de production. Convertis toujours explicitement avec un masque, et précise le paramètre NLS quand le résultat en dépend.

    Lundi 15 Janvier 2024 1 234,56

    Sans le préfixe FM, Day et Month sont complétés par des espaces jusqu'à la longueur du nom le plus long (3 espaces après « Lundi », 2 après « Janvier »). Dans le masque numérique, D et G désignent les séparateurs décimal et de milliers de la session, alors que . et , sont fixes.

    Piège

    WHERE date_embauche = '01/03/2015' fonctionne… tant que NLS_DATE_FORMAT vaut DD/MM/YYYY. Autre piège : comparer une colonne VARCHAR2 à un nombre (WHERE code_postal = 75001). Oracle convertit alors la colonne (TO_NUMBER(code_postal)) : l'index sur la colonne est ignoré, et la requête plante en ORA-01722 dès qu'une ligne contient une valeur non numérique. À l'inverse, WHERE emp_id = '104' convertit le littéral et reste performant, mais autant écrire le bon type.

    Erreurs de conversion fréquentes : ORA-06502: PL/SQL: numeric or value error (exception VALUE_ERROR : chaîne trop longue pour la variable, nombre trop grand pour la précision, texte non numérique converti dans une expression PL/SQL) et ORA-01722: invalid number (INVALID_NUMBER, levée par une conversion dans un ordre SQL). Depuis 12.2, le SQL sait convertir sans lever d'erreur : TO_NUMBER(x DEFAULT NULL ON CONVERSION ERROR), et VALIDATE_CONVERSION(x AS NUMBER) renvoie 1 ou 0. Le traitement des exceptions est au chapitre 05.

    Questions d'entretien

    Différence entre VARCHAR2 et CHAR ?

    CHAR(n) a une longueur fixe et complète avec des espaces ; VARCHAR2(n) stocke la longueur réelle. Avec CHAR, comparer à une variable VARCHAR2 peut échouer à cause des espaces de remplissage. On utilise VARCHAR2 sauf cas très particulier. Bonus : la longueur est en octets par défaut, VARCHAR2(n CHAR) la compte en caractères.

    Différence entre NVL et COALESCE ?

    NVL(a, b) prend exactement deux arguments et évalue toujours les deux ; si les types diffèrent, il convertit b dans le type de a. COALESCE(a, b, c…) accepte une liste, renvoie la première valeur non nulle et s'arrête dès qu'il la trouve (évaluation en court-circuit, utile si b est un appel de fonction coûteux). Il exige des types compatibles et fait partie du standard SQL ANSI.

    Pourquoi PLS_INTEGER plutôt que NUMBER pour un compteur ?

    PLS_INTEGER utilise l'arithmétique native du processeur alors que NUMBER est une représentation décimale logicielle. Le gain est réel dans les boucles serrées. En contrepartie, la plage est limitée à 32 bits signés (de -2 147 483 648 à 2 147 483 647) (au-delà : ORA-01426) et une valeur décimale est arrondie. SIMPLE_INTEGER va plus loin (pas de NULL, pas de contrôle de dépassement).

    DATE ou TIMESTAMP : lequel choisir ?

    Les deux contiennent date et heure. DATE s'arrête à la seconde, n'a pas de fuseau, et la soustraction de deux dates donne un nombre de jours. TIMESTAMP ajoute les fractions de seconde (et le fuseau avec WITH TIME ZONE) ; la soustraction donne un INTERVAL DAY TO SECOND. On prend DATE pour une date métier (embauche, échéance) et TIMESTAMP pour un horodatage technique (journal, ordre d'événements rapprochés, données multi-fuseaux). Dans les deux cas, attention à l'heure cachée lors des comparaisons d'égalité.

    Comment détecter qu'une valeur a changé quand elle peut être NULL ?

    l_ancien != l_nouveau vaut NULL dès qu'un des deux est NULL, donc le passage de NULL à 500 passe inaperçu. Il faut traiter les cas NULL explicitement : l_ancien != l_nouveau OR (l_ancien IS NULL AND l_nouveau IS NOT NULL) OR (l_ancien IS NOT NULL AND l_nouveau IS NULL). En SQL, DECODE(a, b, 0, 1) = 1 fait la même chose car DECODE considère deux NULL comme égaux, mais il n'est pas disponible directement en PL/SQL. Cas typique : un trigger d'audit (chapitre 10).

    Chapitre 03 · 60 min

    Structures de contrôle

    Conditions et boucles sont ce qui distingue PL/SQL du SQL pur. Rien de compliqué ici, mais les tests de lecture de code en entretien adorent leurs détails : une borne de FOR modifiée, un CASE sans ELSE, un WHILE face à NULL.

    • choisir entre IF, CASE instruction et CASE expression, et savoir ce que chacun fait quand rien ne correspond ;
    • tirer parti de l'évaluation en court-circuit de AND et OR ;
    • écrire les trois formes de boucle, en sortir proprement et éviter la boucle infinie ;
    • connaître le comportement exact de la boucle FOR (indice, bornes, REVERSE, portée) ;
    • piloter des boucles imbriquées avec EXIT, CONTINUE et les étiquettes.

    Conditions

    IF, ELSIF, ELSE

    Les branches sont testées dans l'ordre et seule la première condition vraie s'exécute. Une condition qui vaut NULL est traitée comme non vraie : on passe à la branche suivante (la logique à trois valeurs est détaillée au chapitre 02).

    Confirmé
    • Une variable BOOLEAN se teste directement : IF l_trouve THEN, pas IF l_trouve = TRUE THEN.
    • Une branche ne peut pas être vide. Pour dire explicitement « ne rien faire », écris l'instruction NULL;.
    • ELSE IF (en deux mots) compile, mais ouvre un nouveau IF imbriqué qui réclame son propre END IF; : source classique de PLS-00103 en fin de bloc.

    Évaluation en court-circuit

    PL/SQL arrête d'évaluer une expression logique dès que le résultat est connu : dans A AND B, si A est faux, B n'est jamais calculé ; dans A OR B, si A est vrai, B est ignoré. On s'en sert pour protéger un calcul risqué par un test placé avant lui.

    Département vide
    Piège

    L'ordre des opérandes compte. Écrit l_masse / l_nb > 4000 AND l_nb > 0, le même test lève ZERO_DIVIDE (ORA-01476) avant même de regarder l_nb. Le court-circuit vaut pour les conditions PL/SQL ; dans une clause WHERE, c'est l'optimiseur SQL qui choisit l'ordre d'évaluation, ne compte pas dessus.

    Deux CASE différents

    PL/SQL connaît deux formes de CASE : le CASE simple compare une valeur à une liste (CASE l_poste WHEN 'DEV' …) et le CASE recherché évalue des conditions libres (CASE WHEN l_sal > 5000 …). Chacune peut s'utiliser de deux façons, et c'est là que se cache la question d'entretien.

    Instruction CASEExpression CASE
    RôleExécute des instructionsRenvoie une valeur (dans une affectation, un appel, un SELECT)
    FinEND CASE;END
    BranchesUne ou plusieurs instructions terminées par ;Une expression, toutes du même type (ou convertibles)

    Dans les deux cas, c'est la première branche vraie qui gagne : les suivantes ne sont pas évaluées.

    Accès production
    ORA-06592: CASE not found while executing CASE statement
    Piège

    CASE l_x WHEN NULL THEN … ne fonctionne jamais : le CASE simple compare avec =, et NULL = NULL n'est pas vrai. Pour tester NULL, utilise le CASE recherché : CASE WHEN l_x IS NULL THEN ….

    En entretien

    « IF ou CASE ? » Les deux sont équivalents en puissance. CASE est plus lisible quand on teste une même valeur contre une liste, et l'expression CASE évite de répéter l'affectation dans chaque branche. IF reste naturel pour des conditions hétérogènes. Ajoute un ELSE à toute instruction CASE dont tu n'es pas sûr qu'elle couvre tous les cas.

    Piège : la boucle infinie

    Les deux causes classiques : oublier d'incrémenter le compteur, et une condition de sortie qui vaut NULL. Avec l_max NULL, EXIT WHEN i > l_max n'est jamais vrai, donc la boucle ne s'arrête jamais ; à l'inverse, WHILE i <= l_max ne fait aucun tour, sans la moindre erreur. Initialise tes variables et, pour une boucle dont tu ne maîtrises pas la fin, ajoute un garde-fou (EXIT WHEN l_tours > 10000;).

    Il existe une quatrième forme très courante, FOR r IN (SELECT …) LOOP, qui parcourt le résultat d'une requête : c'est la boucle FOR de curseur, traitée au chapitre 04.

    Ce qu'il faut savoir sur FOR

    • L'indice est déclaré implicitement en PLS_INTEGER, n'existe que dans la boucle et est en lecture seule : j := 5 provoque PLS-00363 à la compilation.
    • Les bornes sont évaluées une seule fois à l'entrée et converties en PLS_INTEGER, donc arrondies à l'entier le plus proche si ce ne sont pas des entiers (FOR i IN 1 .. 2.5 fait 3 tours) : modifier la variable de borne dans la boucle ne change pas le nombre de tours.
    • Si la borne basse dépasse la borne haute (FOR i IN 5 .. 1), la boucle ne s'exécute pas du tout, sans erreur. Pour descendre : REVERSE 1 .. 5 (la borne basse reste à gauche).
    • Si une variable porte déjà le nom de l'indice, l'indice la masque dans la boucle sans la modifier. Après la boucle, on retrouve l'ancienne valeur.
    tour 1 tour 2 tour 3 i = 99, l_fin = 10

    Le pas est toujours de 1 jusqu'en 19c. Depuis 21c (donc en 23ai), la clause BY fixe un pas strictement positif (FOR i IN 1 .. 10 BY 3, la borne haute reste une limite et n'est pas forcément atteinte), et d'autres contrôles d'itération sont apparus (plusieurs plages séparées par des virgules, filtre WHEN, parcours de collection avec VALUES OF / INDICES OF). En 19c, on calcule la valeur à partir de l'indice.

    1 4 7 10 1 4 7 10

    CONTINUE, EXIT et étiquettes

    EXIT sort de la boucle ; CONTINUE (depuis 11g) abandonne l'itération en cours et passe à la suivante. Les deux ont une forme conditionnelle, EXIT WHEN cond et CONTINUE WHEN cond, plus lisible qu'un IF … THEN EXIT; END IF;. Dans une boucle FOR ou WHILE, ils fonctionnent exactement comme dans un LOOP.

    Sans précision, EXIT et CONTINUE agissent sur la boucle la plus interne. Pour agir sur une boucle englobante, on lui donne une étiquette <<nom>> juste avant le mot-clé de boucle, puis on écrit EXIT nom ou CONTINUE nom. Répéter le nom après END LOOP est facultatif mais aide à la lecture.

    1 2 4 3 6 9 4 8

    Une ligne commencée avec DBMS_OUTPUT.PUT n'est récupérée par le client que lorsqu'un NEW_LINE (ou un PUT_LINE) la termine : sans le NEW_LINE avant EXIT lignes, « 4 8 » n'apparaîtrait pas à la fin de ce bloc.

    Astuce

    GOTO existe mais n'a quasiment jamais sa place : un recruteur verra son usage comme un signal négatif. Préfère EXIT, CONTINUE, une étiquette de boucle ou un sous-programme.

    En entretien

    Une boucle qui exécute un ordre SQL à chaque tour est le premier réflexe à questionner. Si tu peux écrire le traitement en un seul UPDATE ou INSERT … SELECT, c'est presque toujours mieux ; sinon, on passe aux traitements en masse (chapitre 09).

    Questions d'entretien

    Quelle différence entre EXIT et CONTINUE ?

    EXIT quitte la boucle ; CONTINUE (depuis 11g) abandonne l'itération en cours et passe à la suivante. Les deux acceptent une forme conditionnelle (EXIT WHEN / CONTINUE WHEN) et une étiquette pour viser une boucle englobante (EXIT ext, CONTINUE ext). Sans étiquette, ils agissent sur la boucle la plus interne.

    Que fait un CASE sans ELSE quand aucune branche ne correspond ?

    Ça dépend de la forme. L'instruction CASE … END CASE; lève CASE_NOT_FOUND (ORA-06592). L'expression CASE … END renvoie simplement NULL, comme en SQL. Bonne pratique : toujours prévoir un ELSE, quitte à y lever une erreur explicite.

    LOOP, WHILE ou FOR : comment choisis-tu ?

    FOR quand le nombre de tours est connu à l'entrée : pas de compteur à gérer, pas de boucle infinie possible. WHILE quand on peut ne faire aucun tour et que la condition se teste avant. LOOP … EXIT WHEN quand la sortie se décide au milieu ou à la fin du corps (au moins un passage). Pour parcourir le résultat d'une requête, la boucle FOR de curseur, voire BULK COLLECT ; et si le traitement s'écrit en un seul ordre SQL, pas de boucle du tout.

    Que se passe-t-il si on modifie l'indice ou une borne d'une boucle FOR ?

    Affecter l'indice est refusé à la compilation (PLS-00363, l'indice est en lecture seule). Modifier la variable utilisée comme borne est permis mais sans effet : les bornes sont évaluées une seule fois, à l'entrée. Pour arrêter plus tôt, on utilise EXIT. Bonus : l'indice n'existe que dans la boucle, et s'il porte le nom d'une variable existante, il la masque sans la modifier.

    PL/SQL évalue-t-il AND et OR en court-circuit ?

    Oui : dès que le résultat est connu, le reste de l'expression n'est pas évalué. IF l_nb > 0 AND l_total / l_nb > 100 ne divise donc jamais par zéro, alors que l'ordre inverse lève ZERO_DIVIDE. CASE s'arrête aussi à la première branche vraie. En SQL en revanche, l'ordre d'évaluation d'un WHERE appartient à l'optimiseur.

    Chapitre 04 · 75 min

    SQL dans PL/SQL et curseurs

    Un curseur est une zone de travail où Oracle exécute une requête et garde sa position dans le résultat. Chaque ordre SQL de ton code en utilise un, que tu le déclares ou non. En entretien, on te demandera presque toujours la différence entre curseur implicite et explicite, les exceptions de SELECT INTO et le rôle de FOR UPDATE.

    • utiliser SELECT INTO sans être surpris par ses deux exceptions ;
    • lire les attributs SQL%ROWCOUNT, %FOUND, %NOTFOUND, %ISOPEN ;
    • dérouler le cycle de vie d'un curseur explicite, puis le remplacer par une boucle FOR ;
    • verrouiller avec FOR UPDATE (et SKIP LOCKED) et renvoyer un résultat au client avec SYS_REFCURSOR ;
    • choisir le bon type de curseur selon la situation.

    SELECT INTO : exactement une ligne

    SELECT … INTO utilise un curseur implicite et doit ramener une et une seule ligne. Les variables de destination doivent correspondre en nombre et en type aux colonnes (ou être un record : SELECT * INTO r_emp avec r_emp employes%ROWTYPE).

    Piège classique d'entretien

    Une requête d'agrégat sans GROUP BY renvoie toujours une ligne. SELECT COUNT(*) INTO l_n FROM employes WHERE dept_id = 40 ne lève jamais NO_DATA_FOUND : l_n vaut 0. Et SELECT MAX(salaire) … sur zéro ligne donne NULL, sans exception. À l'inverse, avec un GROUP BY, zéro groupe signifie zéro ligne, donc NO_DATA_FOUND.

    Astuce : tester l'existence

    Pour savoir si au moins une ligne existe, ne compte pas tout : SELECT COUNT(*) INTO l_n FROM employes WHERE dept_id = p_dept AND ROWNUM = 1 renvoie 0 ou 1 et s'arrête à la première ligne trouvée. Souvent, le plus simple reste de tenter directement l'action (un UPDATE puis SQL%ROWCOUNT) plutôt que de vérifier avant d'agir.

    DML et curseur implicite

    Après chaque INSERT, UPDATE, DELETE, MERGE ou SELECT INTO, les attributs du curseur implicite SQL décrivent le dernier ordre exécuté. Tant qu'aucun ordre SQL n'a été exécuté, ils valent NULL (sauf SQL%ISOPEN, toujours FALSE).

    AttributSignification

    SQL%NOTFOUNDTRUE si aucune ligne n'a été touchée
    SQL%ISOPENToujours FALSE : Oracle ferme le curseur implicite aussitôt l'ordre terminé

    Piège

    Lis SQL%ROWCOUNT immédiatement après l'ordre. Un autre ordre SQL exécuté entre-temps, même caché dans une procédure appelée (un journal d'audit par exemple), l'écrase. Copie-le dans une variable si tu en as besoin plus loin.

    En entretien

    « Un UPDATE qui ne trouve aucune ligne lève-t-il une exception ? » Non : seul SELECT INTO lève NO_DATA_FOUND. Pour un DML, c'est à toi de tester SQL%ROWCOUNT = 0 ou SQL%NOTFOUND et de lever une erreur si c'est anormal.

    Pour parcourir plusieurs lignes, on déclare un curseur nommé. Son cycle de vie a quatre étapes : déclarer, ouvrir (la requête s'exécute et l'image des données est figée), lire ligne par ligne avec FETCH, fermer.

    FOR UPDATE pose un verrou sur toutes les lignes sélectionnées dès l'OPEN (sauf avec SKIP LOCKED, voir plus bas), jusqu'au COMMIT ou ROLLBACK. Personne ne peut les modifier entre ta lecture et ta mise à jour : c'est la protection contre la mise à jour perdue.     Questions d'entretien

    Différence entre curseur implicite et explicite ?

    Le curseur implicite est créé et géré par Oracle pour chaque ordre SQL (SELECT INTO, DML) ; on lit ses attributs via SQL%, qui décrivent toujours le dernier ordre exécuté. Le curseur explicite est déclaré par le développeur pour une requête multi-lignes, avec un contrôle complet du cycle OPEN / FETCH / CLOSE et des attributs nom%. La boucle FOR de curseur combine les deux avantages : curseur nommé ou en ligne, ouverture et fermeture automatiques, lecture par paquets de 100. Elle est le choix par défaut ; on garde l'explicite pour le FETCH … BULK COLLECT LIMIT ou un contrôle fin.

    Qu'est-ce qu'un REF CURSOR et à quoi sert-il ?

    Une variable qui pointe vers un curseur ouvert. Elle permet d'ouvrir des requêtes différentes à l'exécution (y compris dynamiques) et surtout de passer un jeu de résultats d'une procédure stockée à une application cliente, qui lit les lignes au fil de l'eau sans tout charger en mémoire côté serveur. Fort : structure vérifiée à la compilation. Faible (SYS_REFCURSOR) : n'importe quelle requête. L'appelant doit le fermer.

    À quoi servent FOR UPDATE et WHERE CURRENT OF ?

    FOR UPDATE verrouille les lignes à l'ouverture du curseur pour éviter qu'une autre session ne les modifie entre la lecture et la mise à jour (mise à jour perdue). Les verrous tiennent jusqu'au COMMIT ou ROLLBACK ; un COMMIT dans la boucle libère tous les verrous et un FETCH ultérieur sur ce curseur lève ORA-01002. WHERE CURRENT OF cible la ligne courante du curseur via son ROWID, sans nouvelle recherche. Options : NOWAIT, WAIT n, SKIP LOCKED.

    Comment plusieurs sessions peuvent-elles traiter une même table de tâches sans se bloquer ?

    Avec SELECT … FOR UPDATE SKIP LOCKED : chaque session verrouille les lignes libres et saute celles déjà prises par les autres, sans attendre. Point à citer : ne pas limiter avec ROWNUM (appliqué avant le saut des lignes verrouillées), mais ouvrir le curseur et ne lire que le nombre de lignes voulu (FETCH … LIMIT n).

    Que renvoie SQL%ROWCOUNT après un SELECT INTO ?

    1 s'il a réussi, 0 s'il a levé NO_DATA_FOUND. Cas piège : quand il lève TOO_MANY_ROWS, SQL%ROWCOUNT vaut aussi 1 (comportement documenté par Oracle), et non le nombre réel de lignes qui satisfont la requête.

    Gestion des exceptions

    Tous les entretiens PL/SQL y passent. Il faut savoir lever, intercepter, transformer et journaliser une erreur, et surtout expliquer où elle va quand personne ne l'intercepte et ce qu'elle annule au passage.

    • intercepter les exceptions prédéfinies et en déclarer de nouvelles ;
    • nommer une erreur Oracle avec PRAGMA EXCEPTION_INIT ;
    • lever une erreur métier avec RAISE_APPLICATION_ERROR et re-lever avec RAISE ;
    • prédire la propagation d'une exception et ce qui est annulé dans la transaction ;
    • journaliser une erreur avec sa ligne d'origine.

    La section EXCEPTION

    Quand une erreur survient dans la section BEGIN, l'exécution quitte immédiatement l'instruction en cours et saute à la section EXCEPTION du même bloc. Oracle cherche le gestionnaire WHEN qui correspond ; WHEN OTHERS attrape tout ce qui reste et doit être le dernier (sinon erreur de compilation). Les instructions situées entre la ligne fautive et EXCEPTION ne sont jamais exécutées.

    1. Exception utilisateur + RAISE

    Propagation : où va l'exception ?

    Si le bloc courant n'a pas de gestionnaire adapté, l'exception remonte au bloc englobant, puis à l'appelant, et ainsi de suite jusqu'au client. Trois règles à connaître par cœur :

    1. Une exception levée dans la section DECLARE (initialisation invalide) n'est pas traitée par la section EXCEPTION du même bloc : elle part directement au bloc englobant.
    2. Une exception levée dans un gestionnaire EXCEPTION (y compris par RAISE ou RAISE_APPLICATION_ERROR) part aussi directement au bloc englobant.
    3. Une fois l'exception traitée, l'exécution reprend après le bloc qui l'a traitée, jamais à la ligne qui l'a levée.

    Exceptions et transaction : qu'est-ce qui est annulé ?

    Oracle garantit l'atomicité au niveau de l'instruction : un ordre DML qui échoue est annulé à lui seul (les lignes qu'il avait déjà modifiées sont restaurées), mais les ordres réussis avant lui restent en place. Pour le client, un bloc anonyme ou un EXEC est un seul appel : si une exception remonte jusqu'à lui, Oracle annule tout ce que cet appel a modifié, mais rien de ce qui avait été fait avant dans la même transaction.

    Piège : une procédure qui échoue n'annule pas son propre travail

    Si une procédure appelée lève une exception et que l'appelant PL/SQL l'intercepte, les DML déjà faits par la procédure ne sont pas annulés : seul l'ordre fautif l'est. Ses paramètres OUT ne sont pas non plus renseignés (sauf ceux passés avec NOCOPY, qui peuvent garder une valeur partielle ; voir le chapitre 06). Si tu veux un « tout ou rien » pour la procédure, pose un SAVEPOINT au début et fais ROLLBACK TO ce point dans le gestionnaire avant de re-lever (chapitre 11).

    En entretien : « Que devient la transaction si une exception n'est pas traitée ? »

    Réponds en trois temps. 1) L'ordre fautif est toujours annulé (rollback au niveau instruction). 2) Si l'exception remonte jusqu'au client, tout ce que l'appel (bloc anonyme, EXEC) a modifié est annulé, mais pas le travail antérieur de la transaction, qui reste ouverte. 3) Si l'exception est traitée dans le code, rien d'autre n'est annulé automatiquement : c'est au développeur de décider (ROLLBACK, ROLLBACK TO SAVEPOINT ou rien).

    Exceptions dans une boucle

    Une exception non traitée dans le corps d'une boucle la quitte immédiatement : les tours restants n'ont pas lieu. Pour continuer malgré une erreur sur une ligne, encapsule le traitement de la ligne dans un sous-bloc BEGIN … EXCEPTION … END; à l'intérieur de la boucle. L'erreur est traitée localement et la boucle reprend au tour suivant.

    105 : OK 106 : OK 107 : ORA-02290: check constraint (RH.CK_EMP_SALAIRE) violated 108 : ORA-02290: check constraint (RH.CK_EMP_SALAIRE) violated

    Le préfixe RH. est le nom du schéma propriétaire de la table. Pour de gros volumes, on préfère FORALL … SAVE EXCEPTIONS (chapitre 09).

    Journaliser correctement une erreur

    SQLERRM donne le message, mais pas la ligne d'origine. DBMS_UTILITY.FORMAT_ERROR_BACKTRACE donne la pile des numéros de ligne jusqu'à l'endroit où l'erreur a été levée : indispensable en production.

    ORA-02290: check constraint (RH.CK_EMP_SALAIRE) violated ORA-06512: at line 6

    Remarque la ligne 6 du bloc anonyme : c'est celle du RAISE, pas celle de l'UPDATE (ligne 2). RAISE; conserve le code et le message d'origine, mais l'information de ligne repart du point où l'exception est re-levée : ce que voient ensuite le client, un gestionnaire englobant ou un FORMAT_ERROR_BACKTRACE appelé plus haut, c'est la ligne du RAISE. La ligne d'origine est perdue. Le journal, lui, a lu le backtrace dans le gestionnaire, avant le RAISE : il contient ORA-06512: at line 2.

    Nuance : ce n'est pas la propagation qui efface la trace. Tant qu'aucun gestionnaire ne l'intercepte, l'exception remonte avec toute sa pile (une ligne ORA-06512 par niveau traversé). C'est l'interception suivie d'une nouvelle levée (RAISE;, RAISE e_nom; ou RAISE_APPLICATION_ERROR) qui fait repartir le backtrace de ce point. D'où la règle : journalise le backtrace dans le premier gestionnaire qui intercepte l'erreur, avant de re-lever.

    UTL_CALL_STACK (12c) : la même information, structurée

    Le package UTL_CALL_STACK expose la pile d'erreurs (numéro, message) et le backtrace (unité, ligne) niveau par niveau, sans analyser de texte. Pour la pile d'appels, il va plus loin que FORMAT_CALL_STACK : il donne le nom du sous-programme à l'intérieur d'un package (pkg_rh.augmenter), là où les fonctions de DBMS_UTILITY ne citent que le package. Pour le backtrace, en revanche, il ne fournit que l'unité et la ligne.

    Pour la pile d'appels (qui appelle qui, même sans erreur), on utilise UTL_CALL_STACK.DYNAMIC_DEPTH et CONCATENATE_SUBPROGRAM(SUBPROGRAM(i)), ou l'ancien DBMS_UTILITY.FORMAT_CALL_STACK.

    L'anti-pattern n°1 : WHEN OTHERS THEN NULL

    Avaler toutes les erreurs sans rien dire masque les bugs, laisse des données à moitié traitées et rend le diagnostic impossible. Quand les avertissements sont activés (ALTER SESSION SET PLSQL_WARNINGS = 'ENABLE:ALL'), le compilateur le signale avec PLW-06009. Règle : un WHEN OTHERS doit se terminer par RAISE ou RAISE_APPLICATION_ERROR, sauf cas très documenté (ex. traitement de masse qui journalise et continue).

    Questions d'entretien

    Différence entre RAISE et RAISE_APPLICATION_ERROR ?

    RAISE lève une exception nommée (prédéfinie ou déclarée), ou re-lève l'exception courante quand il est utilisé seul dans un gestionnaire. RAISE_APPLICATION_ERROR crée une erreur Oracle avec un code entre -20000 et -20999 et un message personnalisé, que l'application cliente reçoit comme une erreur ORA- classique. Une exception utilisateur levée par RAISE et non traitée n'arrive au client que sous la forme ORA-06510, sans message métier.

    Que devient la transaction quand une exception n'est pas traitée ?

    L'ordre fautif est toujours annulé (atomicité au niveau instruction). Si l'exception remonte jusqu'au client, tout ce que l'appel a modifié est annulé, mais pas le travail fait avant l'appel : la transaction reste ouverte. Si l'exception est interceptée dans le code, seuls les effets de l'ordre fautif disparaissent ; le reste attend un COMMIT ou un ROLLBACK explicite.

    Pourquoi WHEN OTHERS THEN NULL est-il dangereux ?

    Il masque toutes les erreurs, y compris celles qu'on n'avait pas prévues (espace disque, verrou, bug). Le programme semble réussir, la transaction peut être validée avec des données incohérentes et personne n'est prévenu. On doit au minimum journaliser puis re-lever.

    Comment retrouver la ligne qui a provoqué une erreur ?

    Avec DBMS_UTILITY.FORMAT_ERROR_BACKTRACE, appelé dans le premier gestionnaire qui intercepte l'erreur et avant de re-lever : après un RAISE, le backtrace repart de la ligne du RAISE et la ligne d'origine est perdue. SQLERRM et FORMAT_ERROR_STACK donnent les messages, pas les lignes. Depuis 12c, UTL_CALL_STACK donne la même information de façon structurée (unité, ligne), et, pour la pile d'appels, le nom des sous-programmes de package.

    À quoi sert PRAGMA EXCEPTION_INIT ?

    À associer un nom d'exception déclaré à un numéro d'erreur Oracle qui n'a pas de nom prédéfini (par exemple -2292 pour une violation de clé étrangère), pour l'intercepter par son nom dans un gestionnaire dédié plutôt que de tester SQLCODE dans WHEN OTHERS. On l'utilise aussi pour nommer ses propres codes -20xxx.

    Piège : OUT et exceptions

    Les paramètres OUT et IN OUT sont recopiés vers l'appelant seulement si le sous-programme se termine normalement.     NOCOPY : passer par référence

    Recopier une collection de 100 000 éléments à l'entrée et à la sortie coûte cher. L'indication NOCOPY demande au compilateur de passer le paramètre OUT ou IN OUT par référence : p_tab IN OUT NOCOPY t_tab. Deux conséquences :

    • ce n'est qu'une indication : Oracle peut l'ignorer, par exemple si la variable passée par l'appelant porte une contrainte (NOT NULL, ou une précision comme NUMBER(8,2)), si une conversion de type implicite est nécessaire, si on passe un élément de tableau associatif plutôt que le tableau entier, ou si l'appel passe par un lien de base de données ;
    • si elle est appliquée, la variable de l'appelant est modifiée au fil de l'exécution : en cas d'exception, elle peut rester à moitié modifiée.

    Réserve-la aux grosses collections et aux LOB, là où le gain est mesurable, et ne fais jamais dépendre la logique de l'appelant du fait qu'elle soit appliquée ou non.

    La notation nommée rend l'appel lisible et robuste : on peut ajouter un paramètre avec valeur par défaut à la fin d'une procédure sans casser les appels existants, et l'ordre des paramètres nommés est libre.     Fonctions appelées depuis SQL

    Le résultat dépend de la date du jour. Exécutée le 27 octobre 2026, la requête renvoie 7 lignes, de Martin (11 ans) à Durand (5 ans) ; Laurent (4 ans), Michel (3) et Garcia (2) sont exclus.

    Pour être appelée depuis SQL, une fonction doit :

    • être stockée (autonome ou publique dans un package) ou déclarée dans la clause WITH de la requête ;
    • n'utiliser que des types SQL en paramètres et retour : pas de record PL/SQL, pas de tableau associatif, pas de BOOLEAN avant 23ai (où BOOLEAN devient un type SQL) ;
    • n'avoir que des paramètres IN ;
    • appelée depuis un SELECT, ne faire aucun DML (ORA-14551: cannot perform a DML operation inside a query) ;
    • appelée depuis un SELECT ou depuis un ordre DML, ne faire ni COMMIT, ni ROLLBACK, ni DDL (ORA-14552: cannot perform a DDL, commit or rollback inside a query or DML) ; ces deux interdits tombent si la fonction est en transaction autonome (chapitre 11) ;
    • appelée depuis un INSERT, UPDATE ou DELETE, ne pas lire ni modifier la table que cet ordre modifie (table mutante ORA-04091, détaillée au chapitre 10).
    Piège de performance

    Dans la requête ci-dessus, anciennete est appelée pour chaque ligne dans le WHERE, puis de nouveau pour chaque ligne retenue dans le SELECT, et chaque appel exécute un SELECT. Chaque appel est un changement de contexte SQL → PL/SQL, et chaque requête interne un changement PL/SQL → SQL. Sur un million de lignes, c'est catastrophique : écris la logique en SQL pur (TRUNC(MONTHS_BETWEEN(SYSDATE, date_embauche) / 12)), ou fais recevoir à la fonction la date plutôt que l'identifiant.

    Piège : NO_DATA_FOUND avalé par SQL

    Comme vu au chapitre 05, un NO_DATA_FOUND qui s'échappe d'une fonction appelée en SQL donne NULL sans erreur : SELECT anciennete(999) FROM dual affiche une valeur vide. Autre subtilité : la requête interne de la fonction prend sa propre image des données à chaque appel ; elle ne partage pas la lecture cohérente de la requête qui l'appelle.

    OptionEffet

    Piège : un faux DETERMINISTIC

    Une fonction qui lit SYSDATE, une table, une variable de package ou un paramètre NLS n'est pas déterministe. La déclarer DETERMINISTIC compile sans erreur, mais un index sur fonction bâti dessus renverra des résultats faux le jour où la valeur change. C'est pour cela que annees_depuis reçoit la date de fin en paramètre au lieu de lire SYSDATE elle-même. De même, RESULT_CACHE ne convient pas à une fonction qui dépend de l'état de la session.

    Déclaration anticipée et récursivité

    Un sous-programme local doit être déclaré avant d'être appelé. Quand deux sous-programmes s'appellent mutuellement, on écrit d'abord la déclaration anticipée (forward declaration) de l'un : son en-tête seul, terminé par un point-virgule. Un sous-programme peut aussi s'appeler lui-même (récursivité) : il faut alors une condition d'arrêt, sinon chaque appel empile ses variables locales jusqu'à épuiser la mémoire de la session : PL/SQL lève alors STORAGE_ERROR (ORA-06500), ou le serveur une erreur mémoire comme ORA-04030.

    Bernard Petit Garcia Durand Leroy

    Dans SQL*Plus, SET SERVEROUTPUT ON supprime les espaces en début de ligne : utilise SET SERVEROUTPUT ON FORMAT WRAPPED pour voir l'indentation (SQL Developer la conserve).

    Pour un vrai organigramme, une requête hiérarchique (CONNECT BY ou WITH récursif) fait le même travail en un seul ordre SQL, sans une requête par employé. La récursivité PL/SQL reste utile pour parcourir des structures en mémoire (collections, documents JSON).

    Surcharge locale

    Deux sous-programmes locaux du même bloc peuvent porter le même nom s'ils diffèrent par le nombre ou la famille de types de leurs paramètres, par exemple formater(p_sal NUMBER) et formater(p_date DATE). C'est impossible pour des procédures autonomes du schéma (un seul objet par nom). Les règles de la surcharge sont détaillées avec les packages au chapitre 07.

    Dans le dictionnaire : signature et recompilation

    Un sous-programme stocké est un objet du schéma, VALID ou INVALID, recompilé automatiquement au premier appel après une invalidation : ces mécanismes de dépendance sont détaillés au chapitre 01. Ce qui est propre aux procédures et fonctions, c'est la description de leur signature dans USER_ARGUMENTS.

    Pour augmenter_salaire, USER_ARGUMENTS renvoie trois lignes : P_EMP_ID (position 1, IN), P_PCT (position 2, IN, DEFAULTED = 'Y') et P_NOUVEAU (position 3, OUT), toutes de type NUMBER. Les noms sont en majuscules dans le dictionnaire. Cette vue sert à vérifier la signature réellement compilée, par exemple avant de modifier les appels d'une procédure. Pour un sous-programme de package, il faut filtrer en plus sur package_name.

    Piège classique : les rôles

    Les privilèges obtenus via un rôle ne servent pas à compiler du PL/SQL stocké, et ne sont jamais actifs dans une unité AUTHID DEFINER. Une requête qui fonctionne dans SQL Developer (grâce à un SELECT obtenu via un rôle) échoue à la compilation de la procédure avec PL/SQL: ORA-00942: table or view does not exist. Solution : accorder le privilège directement au propriétaire (GRANT SELECT ON rh.employes TO appli). Depuis 12c, on peut aussi accorder un rôle à l'unité PL/SQL elle-même (GRANT role TO PROCEDURE …), surtout utile en AUTHID CURRENT_USER ; ce rôle n'est actif qu'à l'exécution et ne règle donc pas la compilation du SQL statique.

    Questions d'entretien

    Peut-on faire un COMMIT dans une fonction ?

    Techniquement oui si elle est appelée depuis PL/SQL, mais c'est une mauvaise pratique : une fonction calcule, elle ne doit pas avoir d'effet de bord, et elle validerait la transaction de l'appelant sans qu'il le sache. Appelée depuis un SELECT, un DML lève ORA-14551 ; appelée depuis un SELECT ou un ordre DML, un COMMIT lève ORA-14552. La seule exception est la transaction autonome, réservée à des cas comme la journalisation.

    Que devient un paramètre OUT si la procédure lève une exception ?

    Sans NOCOPY, rien n'est recopié : la variable de l'appelant garde sa valeur d'avant l'appel, même si la procédure avait déjà affecté le paramètre. Avec NOCOPY, le passage peut se faire par référence et la variable peut rester partiellement modifiée ; comme NOCOPY n'est qu'une indication, l'appelant ne doit compter sur aucun des deux comportements.

    Différence entre DETERMINISTIC et RESULT_CACHE ?

    DETERMINISTIC est une promesse faite à Oracle que la fonction renvoie toujours la même chose pour les mêmes entrées ; Oracle ne la vérifie pas, le bénéfice se limite à l'exécution de la requête dans la session, et c'est requis pour un index sur fonction. RESULT_CACHE stocke réellement les résultats dans la SGA, les partage entre sessions et les invalide quand les tables lues sont modifiées et validées : il convient à une fonction qui lit des données rarement modifiées.

    Ma procédure ne compile pas (ORA-00942) alors que la requête marche dans SQL Developer. Pourquoi ?

    Le privilège sur la table est obtenu via un rôle. Les rôles ne sont pas pris en compte pour compiler du PL/SQL stocké ni à l'exécution d'une unité AUTHID DEFINER. Il faut un GRANT direct au propriétaire de la procédure. En AUTHID CURRENT_USER, les rôles de l'appelant sont actifs à l'exécution, mais la compilation demande toujours des privilèges directs (ou du SQL dynamique).

    Une procédure peut-elle renvoyer une valeur ?

    Pas avec RETURN valeur (un RETURN; seul y sert à sortir immédiatement). Elle renvoie des valeurs via des paramètres OUT / IN OUT, ou un SYS_REFCURSOR en OUT pour un jeu de résultats. Si elle doit être utilisable dans une expression ou dans un SELECT, c'est une fonction qu'il faut écrire.

    Tout ce qui est déclaré dans la spécification est public. Tout ce qui n'est que dans le corps est privé.

    Un package se crée en deux ordres distincts : d'abord la spécification (CREATE PACKAGE), qui déclare ce que les autres ont le droit d'utiliser, puis le corps (CREATE PACKAGE BODY), qui contient le code. La spécification compile sans le corps ; l'inverse est impossible. Les appelants ne voient que la spécification et s'écrivent pkg_rh.augmenter(…).

    Les en-têtes des sous-programmes publics doivent être identiques dans la spécification et dans le corps (mêmes noms de paramètres, types et modes), sinon le corps ne compile pas (PLS-00323). Une procédure privée comme valider_salaire doit être définie avant d'être appelée dans le corps, ou annoncée plus haut par une déclaration anticipée (forward declaration).

    Piège

    Le troisième paramètre de la seconde version d'augmenter est un BOOLEAN. Avant 23ai, ce type n'existe pas en SQL : cette version n'est appelable que depuis du code PL/SQL. Un CALL SQL ne peut pas l'atteindre, et une application cliente passe par un bloc anonyme BEGIN pkg_rh.augmenter(20, 5, TRUE); END;. Depuis 23ai, BOOLEAN est aussi un type SQL. Dans du vrai code, un nom explicite (augmenter_dept) serait plus sûr.

    Pourquoi des packages ?

    AvantageExplication
    EncapsulationOn expose une API stable et on cache les détails (procédures privées, variables).
    DépendancesLes appelants dépendent de la spécification. Recompiler le corps n'invalide pas les appelants, ce qui évite les cascades d'invalidation.
    PerformanceAu premier appel, tout le package est chargé dans la mémoire partagée (shared pool) : les appels suivants à ses autres sous-programmes n'ont rien à recharger.
    État de sessionLes variables de package conservent leur valeur entre les appels, pendant toute la session.
    SurchargePlusieurs sous-programmes de même nom avec des paramètres différents (en nombre, ordre ou famille de types). Impossible pour des procédures autonomes.
    SécuritéUn seul GRANT EXECUTE ON pkg_rh donne accès à toute l'API, sans accès direct aux tables.

    L'état de package et la section d'initialisation

    Les variables, constantes et curseurs déclarés au niveau du package (dans la spécification ou dans le corps, hors de tout sous-programme) forment son état. Chaque session a sa propre copie de cet état, en mémoire de session (UGA) : deux utilisateurs ne partagent jamais g_nb_appels. L'état est créé à la première référence au package dans la session (appel d'un sous-programme ou lecture d'une variable publique) : Oracle initialise les variables, puis exécute une fois la section d'initialisation. Il dure ensuite jusqu'à la fin de la session.

    Piège

    Une variable de package n'est pas partagée entre sessions et n'est pas transactionnelle : un ROLLBACK ne remet pas g_nb_appels à sa valeur précédente. Avec un pool de connexions côté application, une variable de package peut « fuiter » d'un utilisateur web à l'autre qui réutilise la même session : réinitialise-la explicitement, ou ne t'en sers pas pour des données propres à un utilisateur.

    ORA-04068 : l'état a été jeté

    Si un package a un état et qu'on recompile son corps (un déploiement, par exemple) pendant que des sessions l'ont déjà instancié, chacune de ces sessions reçoit une erreur à son prochain appel. Voici ce qu'affiche SQL*Plus en 19c pour un EXEC pkg_rh.augmenter(103, 5) (23ai formule les messages un peu différemment et ajoute un lien d'aide) :

    ORA-04068: existing state of packages has been discarded ORA-04061: existing state of package body "RH.PKG_RH" has been invalidated ORA-04065: not executed, altered or dropped package body "RH.PKG_RH" ORA-06508: PL/SQL: could not find program unit being called: "RH.PKG_RH" ORA-06512: at line 1

    (RH est ici le schéma propriétaire.) L'appel suivant fonctionne, car le package est instancié à nouveau, mais les valeurs des variables sont perdues. Les remèdes :

    • éviter les variables globales quand elles ne servent à rien : un package sans état n'a pas ce problème. Depuis 11.2.0.2, un package dont les seuls éléments d'état sont des constantes connues à la compilation (valeur littérale ou expression statique, comme c_smic) est traité comme sans état. Ce n'est pas le cas de pkg_rh, à cause de g_nb_appels ;
    • isoler l'état dans un petit package séparé, rarement modifié, et garder la logique dans un package sans état qu'on peut redéployer ;
    • côté application, intercepter ORA-04068 et relancer l'appel une fois ;
    • pour des déploiements sans interruption : l'Edition-Based Redefinition (11gR2).
    En entretien

    « Recompiler un corps de package n'invalide pas les appelants » et « recompiler un corps de package avec état provoque ORA-04068 dans les sessions qui l'utilisent » sont deux affirmations vraies en même temps. La première concerne les dépendances (statut VALID/INVALID des objets), la seconde l'état en mémoire des sessions. Savoir les distinguer fait bonne impression.

    Quiz

    Questions d'entretien

    Peut-on avoir une spécification sans corps ?

    Oui, si elle ne déclare que des éléments sans implémentation : constantes, types, exceptions, variables. C'est courant pour un package de constantes ou de types partagés. Le corps devient obligatoire dès qu'on déclare un sous-programme ou un curseur avec requête cachée.

    Si je modifie le corps d'un package, les procédures qui l'appellent deviennent-elles invalides ?

    Non. Elles dépendent de la spécification, pas du corps. Seule une modification de la spécification peut invalider les appelants, et depuis 11g le suivi fin des dépendances (fine-grained dependency tracking) les épargne si les éléments qu'ils utilisent n'ont pas changé, par exemple quand on ajoute un nouveau sous-programme à la spécification. C'est un des principaux arguments en faveur des packages.

    Quelles sont les règles de la surcharge ?

    Les versions doivent différer par le nombre, l'ordre ou la famille de types des paramètres. Différer uniquement par le mode (IN/OUT), par le type de retour, ou par des sous-types de la même famille (NUMBER / INTEGER) rend l'appel ambigu : PLS-00307: too many declarations of 'X' match this call. Si seuls les noms des paramètres diffèrent, l'appel positionnel est ambigu mais la notation nommée (p(x => 1)) permet de choisir. On peut surcharger des sous-programmes de package ou locaux, pas des procédures autonomes.

    Qu'est-ce que SERIALLY_REUSABLE ?

    Un PRAGMA qui limite la durée de vie de l'état d'un package à un seul appel serveur au lieu de toute la session. Il économise de la mémoire dans les systèmes avec beaucoup de sessions, mais le package ne peut alors pas être utilisé depuis un trigger ni depuis une fonction appelée par une requête SQL.

    Après un déploiement, des utilisateurs reçoivent ORA-04068 une fois, puis tout refonctionne. Que s'est-il passé ?

    Le corps d'un package avec état (variables globales) a été recompilé alors que leurs sessions l'avaient déjà instancié. Oracle jette l'état de ces sessions : le premier appel échoue, le suivant réinstancie le package et fonctionne, mais les valeurs des variables sont perdues. Pour l'éviter : packages sans état, état isolé dans un package séparé, relance automatique côté application, ou Edition-Based Redefinition.

    Records et collections

    Les collections sont les tableaux de PL/SQL. Elles sont indispensables pour le traitement en masse (chapitre 09) et reviennent souvent en entretien sous la forme « quelle différence entre… » ou « que se passe-t-il si… ».

    Quiz

    Questions d'entretien

    Quelles sont les différences entre les trois types de collections ?

    Le tableau associatif est purement PL/SQL, sans initialisation, indexé par entier ou chaîne, creux possible : c'est le choix par défaut pour un cache ou un BULK COLLECT. La table imbriquée doit être initialisée, peut devenir creuse et peut être un type SQL (colonne, TABLE(), MULTISET, comparaison avec =). Le VARRAY a une taille maximale, reste dense, conserve l'ordre et peut aussi être un type SQL.

    Que signifient ORA-06531, ORA-06532 et ORA-06533 ?

    ORA-06531 « Reference to uninitialized collection » : table imbriquée ou VARRAY utilisé sans constructeur ; correctif l := t_type();. ORA-06532 « Subscript outside of limit » : indice hors des bornes légales (0, négatif, au-delà de la limite d'un VARRAY). ORA-06533 « Subscript beyond count » : indice au-delà des cases allouées, il manque un EXTEND. Une clé absente ou un élément supprimé lève, lui, NO_DATA_FOUND.

    Différence entre COUNT et LAST ?

    COUNT est le nombre d'éléments présents ; LAST est le plus grand indice existant. Ils sont égaux pour une collection dense indexée à partir de 1, différents dès qu'elle est creuse. Sur une collection vide, COUNT vaut 0 et LAST vaut NULL.

    Comment parcourir une collection dont on ne sait pas si elle est dense ?

    Avec FIRST puis NEXT dans une boucle WHILE i IS NOT NULL. Cette forme gère la collection vide, les trous laissés par DELETE et les index de type chaîne. FOR i IN 1 .. COUNT n'est sûr que pour une collection dense commençant à 1, comme le résultat d'un BULK COLLECT.

    Peut-on comparer deux collections ou y chercher un élément sans boucle ?

    Oui pour les tables imbriquées d'éléments scalaires : = et <> les comparent comme des multisets (ordre ignoré), MEMBER OF teste l'appartenance, SUBMULTISET OF l'inclusion, IS A SET l'absence de doublons, et MULTISET UNION / INTERSECT / EXCEPT combinent deux collections. Rien de tout cela n'existe pour les tableaux associatifs ni pour la comparaison de VARRAY.

    Performance : BULK COLLECT et FORALL

    Le sujet qui distingue un développeur PL/SQL confirmé. Dès que tu traites des milliers de lignes, la question n'est plus « est-ce que ça marche » mais « combien d'allers-retours entre les moteurs ».

    • expliquer le coût d'un changement de contexte avec un exemple chiffré ;
    • charger des lignes par lots avec BULK COLLECT … LIMIT et savoir pourquoi on teste COUNT = 0 ;
    • écrire en masse avec FORALL et gérer les erreurs ligne par ligne avec SAVE EXCEPTIONS ou LOG ERRORS ;
    • savoir quand le SQL pur bat tout le reste.

    Le problème : ligne par ligne, lent par lent

    PL/SQL et SQL sont deux moteurs distincts. Chaque ordre SQL exécuté depuis PL/SQL provoque un changement de contexte : le moteur PL/SQL passe la main au moteur SQL (avec les variables liées), puis le reprend. Une boucle qui exécute un INSERT à chaque tour paie ce coût une fois par ligne : 100 000 lignes, 100 000 allers-retours. FORALL envoie toutes les lignes au moteur SQL en un seul aller-retour. Lance la course :

    Sur un gros volume, l'écart est couramment d'un ordre de grandeur (facteur 10 ou plus), selon le traitement et la machine. Tom Kyte, l'une des références d'Oracle, résume l'ordre de préférence ainsi :

    1. Fais-le en un seul ordre SQL si c'est possible (INSERT … SELECT, MERGE, UPDATE avec sous-requête).
    2. Sinon, fais-le en PL/SQL par lots (BULK COLLECT + FORALL).
    3. Ligne par ligne seulement quand il n'y a pas d'autre choix.
    Astuce : la boucle FOR de curseur lit déjà par lots

    Depuis 10g, avec PLSQL_OPTIMIZE_LEVEL à 2 (la valeur par défaut) ou plus, le compilateur transforme FOR r IN (SELECT …) LOOP en lecture par paquets de 100 lignes. La lecture est donc déjà optimisée. En revanche, un UPDATE ou un INSERT placé dans la boucle reste exécuté ligne par ligne : c'est là que FORALL fait la différence.

    BULK COLLECT : lire en masse

    BULK COLLECT INTO remplit une ou plusieurs collections en un seul appel. Les types de collections sont détaillés au chapitre 08 ; ici on utilise surtout des tables imbriquées (nested tables) locales.

    ERROR_CODE vaut 2290, pas -2290 : il faut écrire SQLERRM(-ERROR_CODE). Ce message est générique : le nom de la contrainte est perdu ((.)).     En entretien

    On te demandera souvent « comment traiter un million de lignes sans que la première erreur fasse tout échouer ? ».     L'alternative SQL : DML error logging

Limites : sans REJECT LIMIT, la valeur par défaut est 0 (la première erreur fait échouer l'ordre), et certaines erreurs ne sont pas journalisées (contraintes différées notamment).

    Fonctions pipelined

    Une fonction « table » renvoie une collection qu'on interroge avec TABLE(). Le type de retour doit être connu de SQL : le plus simple est un type créé par CREATE TYPE (voir chapitre 08) ; une fonction pipelined accepte aussi un type déclaré dans la spécification d'un package. En mode PIPELINED, elle envoie chaque ligne dès qu'elle est prête (PIPE ROW) au lieu de construire toute la collection en mémoire : la requête appelante commence à recevoir des lignes tout de suite. C'est idéal pour des transformations de données en flux (ETL).

    Questions d'entretien

    Qu'est-ce qu'un changement de contexte et comment le réduire ?

    Le passage du moteur PL/SQL au moteur SQL (et retour) à chaque ordre SQL exécuté depuis PL/SQL, ou à chaque appel de fonction PL/SQL depuis SQL. On le réduit en écrivant un seul ordre SQL ensembliste, en utilisant BULK COLLECT et FORALL, et en évitant les fonctions PL/SQL appelées ligne à ligne dans les requêtes.

    Pourquoi utiliser LIMIT avec BULK COLLECT, et comment sortir de la boucle ?

    Pour borner la mémoire de session : sans LIMIT, tout le résultat est chargé dans la PGA. Une valeur de 100 à 1 000 donne l'essentiel du gain sans risque mémoire. On sort avec EXIT WHEN l_coll.COUNT = 0 juste après le FETCH : %NOTFOUND devient TRUE dès que le dernier lot est incomplet, et le tester à cet endroit ferait perdre ces lignes.

    FORALL est-il une boucle ?

    Non. C'est une instruction qui envoie un seul ordre DML au moteur SQL avec un tableau de valeurs liées. Il ne peut contenir qu'un seul DML, pas de logique procédurale. SQL%BULK_ROWCOUNT(i) donne ensuite le nombre de lignes touchées par chaque itération.

    Que se passe-t-il quand une ligne échoue dans un FORALL sans SAVE EXCEPTIONS ?

    Le FORALL s'arrête à cette itération et lève l'exception. Seule l'itération fautive est annulée (rollback au niveau de l'instruction) ; les itérations précédentes restent faites dans la transaction tant que personne ne fait de ROLLBACK, et les suivantes ne sont pas exécutées. Si l'exception n'est pas traitée et remonte jusqu'au client, tout le travail de l'appel est annulé.

    Comment traiter un gros volume en gardant les lignes valides malgré des erreurs ?

    En PL/SQL : FORALL … SAVE EXCEPTIONS, puis dans le gestionnaire de ORA-24381, parcourir SQL%BULK_EXCEPTIONS (ERROR_INDEX pour retrouver la ligne, ERROR_CODE positif à passer en négatif à SQLERRM) et journaliser. En SQL pur : LOG ERRORS INTO err$_… REJECT LIMIT UNLIMITED, qui garde le message complet et survit au ROLLBACK.

    La table mutante (ORA-04091)

    Un trigger de ligne ne peut pas lire ni modifier la table sur laquelle il est en train de se déclencher : elle est « en mutation », son contenu est incohérent au milieu de l'ordre DML.

    Le trigger compile sans problème : l'erreur n'apparaît qu'à l'exécution, et l'UPDATE entier est annulé. Le numéro de ligne (4) se compte depuis le DECLARE du trigger, pas depuis le CREATE.

    Un INSERT … VALUES d'une seule ligne ne provoque pas ORA-04091 dans un trigger de ligne : les tests unitaires passent, puis tout casse en production sur un INSERT … SELECT ou un chargement en masse.     Le premier UPDATE réussit. Le second est évalué sur les salaires déjà augmentés de 1 % : moyenne (7 272 + 4 343 + 3 939 + 4 848 + 40 000) / 5 = 12 080,4, plafond 36 241,2. Il échoue donc (la pile se poursuit avec ORA-06512 et ORA-04088) et seul cet ordre est annulé. Les variables déclarées en tête d'un trigger composé sont réinitialisées à chaque ordre DML : pas de fuite d'un ordre à l'autre, contrairement à une variable de package.

    Autres solutions à citer

    Avant 11g : un package avec une collection, un trigger de ligne qui la remplit et un trigger d'instruction qui la traite. Souvent, la meilleure réponse est de sortir la règle du trigger : la mettre dans la procédure d'API qui fait la mise à jour, ou dans une contrainte déclarative quand c'est possible.

    Bonnes pratiques

    • Pas de COMMIT ni ROLLBACK dans un trigger (ORA-04092), sauf transaction autonome réservée au log (voir chapitre 11).
    • Si un trigger lève une exception, tout l'ordre DML est annulé, y compris le travail déjà fait par les autres triggers (rollback au niveau instruction). La transaction, elle, continue : les ordres précédents ne sont pas annulés.
    • Garde les triggers courts : appelle une procédure de package plutôt que d'écrire 200 lignes dedans.
    • Préfère une contrainte (CHECK, FOREIGN KEY, UNIQUE) à un trigger quand elle suffit : plus rapide, plus fiable, visible.
    • Évite la logique métier « cachée » en cascade de triggers : difficile à déboguer, à tester et à faire évoluer.
    • Si plusieurs triggers du même type existent, impose l'ordre avec FOLLOWS (11g) ; sans cette clause, leur ordre n'est pas garanti.
    • Désactiver temporairement : ALTER TRIGGER … DISABLE ou ALTER TABLE … DISABLE ALL TRIGGERS (chargements massifs).

    Quiz

    Questions d'entretien

    Qu'est-ce qu'une table mutante et comment l'éviter ?

    Une table en cours de modification par l'ordre DML qui a déclenché un trigger de ligne. Le trigger ne peut pas la lire ni la modifier : ORA-04091. Solutions : trigger composé (stocker en section ligne, traiter en AFTER STATEMENT), trigger d'instruction, ou déplacer la règle hors du trigger.

    Peut-on modifier :NEW dans un trigger AFTER ?

    Non. :NEW n'est modifiable que dans un trigger BEFORE … FOR EACH ROW, car la ligne n'est pas encore écrite. Dans un AFTER, il est en lecture seule (ORA-04084 à la compilation). :OLD n'est jamais modifiable.

    Dans quel ordre se déclenchent les triggers ?

    BEFORE STATEMENT, puis pour chaque ligne BEFORE ROW, écriture de la ligne, AFTER ROW, enfin AFTER STATEMENT. Pour plusieurs triggers du même type, l'ordre n'est pas garanti sans FOLLOWS (11g). L'ordre de traitement des lignes, lui, n'est jamais garanti.

    Que devient l'ordre DML quand un trigger lève une exception ?

    L'ordre DML entier est annulé, avec tout ce que ses triggers avaient déjà fait (rollback au niveau instruction). La transaction reste ouverte : les ordres précédents ne sont pas perdus, l'appelant décide de valider ou d'annuler. Seul ce qui a été écrit dans une transaction autonome (un journal d'erreurs, par exemple) survit.

    Trigger ou contrainte : que choisis-tu pour une règle métier ?

    Une contrainte déclarative (CHECK, FOREIGN KEY, UNIQUE) dès qu'elle suffit : elle est plus rapide, toujours active, sûre en concurrence et visible dans le dictionnaire. Le trigger sert quand la règle porte sur plusieurs lignes ou plusieurs tables, ou pour l'audit. Même alors, beaucoup d'équipes préfèrent placer la règle dans l'API PL/SQL (un package) qui fait les mises à jour, pour éviter la logique cachée. Une règle multi-lignes en trigger doit aussi gérer la concurrence (verrou), sinon deux sessions peuvent la violer ensemble.

    Chapitre 11 · 65 min

    Transactions et SQL dynamique

    Deux sujets qui touchent à la robustesse et qui reviennent dans presque tous les entretiens : qui décide de valider, comment journaliser une erreur qui sera annulée, et comment construire du SQL à l'exécution sans ouvrir une faille de sécurité.

    • maîtriser COMMIT, ROLLBACK, SAVEPOINT et savoir qui doit valider ;
    • expliquer la lecture cohérente, les niveaux d'isolation et l'interblocage (ORA-00060) ;
    • utiliser une transaction autonome pour la journalisation, et seulement pour ça ;
    • écrire du SQL dynamique avec EXECUTE IMMEDIATE et des variables liées ;
    • expliquer et empêcher une injection SQL.

    Transactions

    Une transaction commence au premier ordre qui modifie des données (INSERT, UPDATE, DELETE, MERGE, SELECT … FOR UPDATE) et se termine par COMMIT (validation) ou ROLLBACK (annulation). Tant qu'elle n'est pas validée, les autres sessions voient les anciennes valeurs (lecture cohérente) et les lignes modifiées sont verrouillées. SAVEPOINT nom pose un repère : ROLLBACK TO SAVEPOINT nom annule le travail fait après ce repère sans terminer la transaction.

    ÉvénementEffet sur la transaction en cours
    COMMITValidée : modifications permanentes et visibles, verrous libérés, savepoints effacés
    ROLLBACKAnnulée entièrement, verrous libérés
    ROLLBACK TO SAVEPOINT spAnnule ce qui suit sp, efface les savepoints posés après lui ; la transaction continue
    Ordre DDL (CREATE, ALTER, DROP, TRUNCATE…)COMMIT implicite avant (et après) l'ordre
    Un ordre DML échoueSeul cet ordre est annulé (atomicité au niveau instruction) ; le reste attend toujours
    Exception non traitée qui remonte au clientTout le travail de l'appel est annulé, pas celui fait avant (voir chapitre 05)
    Fin de sessionNormale : dépend de l'outil (SQL*Plus valide à EXIT par défaut) ; anormale : annulée
    Piège : le DDL valide tout ce qui précède

    Un EXECUTE IMMEDIATE 'CREATE TABLE …' ou un TRUNCATE au milieu d'un traitement valide silencieusement tous les DML en attente : le ROLLBACK du bloc EXCEPTION n'aura plus rien à annuler. Le COMMIT d'avant a lieu même si le DDL échoue ensuite à l'exécution (table déjà existante, par exemple) ; seule une erreur de syntaxe, détectée avant l'exécution, ne déclenche pas ce COMMIT. Ne compte donc jamais sur l'échec d'un DDL pour préserver ta transaction.

    En entretien : « Qui doit faire le COMMIT ? »

    L'appelant de plus haut niveau, celui qui connaît le périmètre de l'unité de travail (le service applicatif, le job batch). Une procédure réutilisable ne doit pas valider elle-même : si elle est appelée au milieu d'un traitement plus large, son COMMIT validerait aussi le travail de l'appelant, qui ne pourrait plus tout annuler.

    Piège : COMMIT dans une boucle

    Valider « toutes les 1 000 lignes » est une fausse bonne idée : c'est généralement plus lent (chaque COMMIT déclenche une écriture du journal de reprise et a un coût fixe), un traitement interrompu laisse des données à moitié traitées et difficiles à reprendre, et un curseur ouvert sur des données que tu modifies peut lever ORA-01555: snapshot too old. Sur un curseur FOR UPDATE, c'est ORA-01002 (chapitre 04). Valide une fois, à la fin.

    Lecture cohérente, isolation et verrous

    Oracle garantit que chaque requête voit les données telles qu'elles étaient validées au moment où elle a commencé, même si d'autres sessions les modifient pendant sa lecture (il reconstitue l'ancienne image grâce à l'undo). Conséquence : une lecture ne bloque jamais une écriture et une écriture ne bloque jamais une lecture (un SELECT … FOR UPDATE n'est pas une simple lecture : il verrouille les lignes comme une écriture). Seules deux écritures sur la même ligne s'attendent : la seconde patiente jusqu'au COMMIT ou au ROLLBACK de la première.

    Niveau d'isolationCe que voit chaque requêteÀ retenir
    READ COMMITTED (défaut)Les données validées au début de la requêteDeux requêtes successives peuvent voir des résultats différents
    SERIALIZABLELes données validées au début de la transaction, plus ses propres modificationsModifier une ligne changée et validée par un autre depuis le début : ORA-08177: can't serialize access for this transaction
    READ ONLYComme SERIALIZABLE, mais aucun DML permisUtile pour un rapport cohérent sur plusieurs requêtes

    On choisit le niveau avec SET TRANSACTION ISOLATION LEVEL SERIALIZABLE (ou SET TRANSACTION READ ONLY), qui doit être la première instruction de la transaction. Oracle n'a pas de lecture « sale » (READ UNCOMMITTED) : une session ne voit jamais les modifications non validées d'une autre.

    Un interblocage (deadlock) survient quand deux sessions s'attendent mutuellement. Oracle le détecte tout seul en quelques secondes : l'une des sessions reçoit ORA-00060: deadlock detected while waiting for resource, seul son dernier ordre est annulé (pas toute sa transaction) et une trace est écrite sur le serveur. Cette session doit ensuite faire ROLLBACK (ou COMMIT) pour libérer l'autre.

    sequenceDiagram
  participant A as Session A
  participant B as Session B
  A->>A: UPDATE employes … WHERE emp_id = 102 (verrou 102)
  B->>B: UPDATE employes … WHERE emp_id = 103 (verrou 103)
  A->>B: UPDATE … WHERE emp_id = 103 : attend B
  B->>A: UPDATE … WHERE emp_id = 102 : attend A
  Note over A,B: cycle d'attente détecté par Oracle
  A->>A: ORA-00060 : cet UPDATE est annulé, A doit faire ROLLBACK

    Deux sessions qui verrouillent les mêmes lignes dans un ordre différent.

    Éviter les interblocages

    Verrouiller les lignes toujours dans le même ordre (par exemple par clé croissante), garder les transactions courtes, et verrouiller d'avance avec SELECT … FOR UPDATE NOWAIT ou WAIT n quand on veut échouer vite plutôt qu'attendre (chapitre 04). Une clé étrangère sans index est aussi une cause classique de verrous inattendus sur la table enfant.

    Transactions autonomes

    PRAGMA AUTONOMOUS_TRANSACTION fait tourner un sous-programme dans une transaction indépendante : il peut valider sans valider le travail de l'appelant, et un ROLLBACK de l'appelant n'annule pas ce qu'il a validé. C'est le cas de log_erreur, écrite au chapitre 05.

    sequenceDiagram
  participant T as Transaction principale
  participant A as log_erreur (autonome)
  T->>T: UPDATE employes (non validé)
  T->>A: appel log_erreur
  Note over A: transaction séparée
  A->>A: INSERT journal_erreurs
  A->>A: COMMIT (valide seulement le journal)
  A-->>T: retour
  T->>T: ROLLBACK (annule l'UPDATE)
  Note over T,A: le journal reste, l'UPDATE est annulé

    La transaction autonome valide son travail sans toucher à celui de l'appelant.

    Salaire de 102 : 4300 Lignes de journal demo : 1
    Pièges
    • Un sous-programme autonome doit se terminer par COMMIT ou ROLLBACK, sinon ORA-06519: active autonomous transaction detected and rolled back : son travail est annulé et l'erreur remonte à l'appelant.
    • Il ne voit pas les modifications non validées de l'appelant. S'il essaie de modifier une ligne verrouillée par l'appelant, il attend une transaction qui attend elle-même son retour : interblocage, ORA-00060.
    • Il permet techniquement de faire du DML dans une fonction appelée en SQL ou de lire une table mutante dans un trigger, mais c'est un contournement dangereux : il travaille sur des données qui ne sont pas celles de la transaction, et ce qu'il valide reste même si l'appelant annule. Réserve-le au journal et à l'audit.

    SQL dynamique : EXECUTE IMMEDIATE

    Le SQL statique est vérifié à la compilation (existence des tables, des colonnes, des droits). Quand la requête n'est connue qu'à l'exécution (nom de table variable, filtres optionnels, DDL), on construit une chaîne et on l'exécute : les erreurs n'apparaissent alors qu'à l'exécution.

    104 : Leroy 4 lignes modifiées EMPLOYES : 10 lignes Plus de 5000 : Bernard Plus de 5000 : Martin Plus de 5000 : Moreau
    Pourquoi des variables liées ?
    • Sécurité : la valeur n'est jamais interprétée comme du SQL, donc pas d'injection.
    • Performance : WHERE emp_id = :id est analysé une fois et son plan est réutilisé ; WHERE emp_id = 104, = 105… sont autant de requêtes différentes, chacune avec une analyse complète (hard parse), qui saturent le cache partagé.

    En SQL statique dans PL/SQL, chaque variable est automatiquement une variable liée : c'est un avantage gratuit du statique.

    Pièges du SQL dynamique
    • Une variable liée remplace une valeur, jamais un identifiant : 'SELECT COUNT(*) FROM :t' lève ORA-00903: invalid table name.
    • Dans un ordre SQL dynamique, les variables liées sont associées par position, pas par nom : :x écrit deux fois demande deux valeurs dans USING.
    • Pas de point-virgule final dans un ordre SQL ('… WHERE emp_id = :id;' provoque une erreur à l'exécution, typiquement ORA-00911: invalid character en 19c ; le code et le message exacts peuvent varier selon la version). Un bloc PL/SQL dynamique, lui, se termine par END;.

    L'injection SQL

    NORMAL INJECTE ---------- ---------- 2 10

    La valeur reçue est x' OR '1'='1 et la chaîne exécutée devient … WHERE poste = 'x' OR '1'='1' : la condition est toujours vraie, les 10 employés sont comptés. EXECUTE IMMEDIATE n'exécute qu'un seul ordre, donc on ne peut pas enchaîner ; DROP TABLE …, mais un attaquant peut ajouter un UNION SELECT sur une autre table quand la requête renvoie des données, ou glisser une sous-requête pour deviner des informations une réponse à la fois. Les défenses :

    1. Préférer le SQL statique quand c'est possible (ici, il suffit !).
    2. Sinon, variables liées pour toute valeur : '… WHERE poste = :p' INTO l_nb USING p_poste.
    3. Pour un identifiant (table, colonne) qui ne peut pas être lié : valider avec DBMS_ASSERT (SIMPLE_SQL_NAME, SQL_OBJECT_NAME qui vérifie aussi que l'objet existe, ENQUOTE_NAME) ou, mieux, une liste blanche des noms autorisés.
    4. Moindre privilège : un compte applicatif sans droits DDL, et attention aux procédures en droits du propriétaire (AUTHID DEFINER, le défaut) : le SQL injecté s'exécute avec les droits du propriétaire du code, pas de l'appelant.
    En entretien

    Si on te demande « comment éviter l'injection SQL ? », donne les quatre défenses dans cet ordre, en commençant par « je n'utilise le SQL dynamique que s'il est vraiment nécessaire ». Ne propose pas d'échapper les apostrophes à la main avec REPLACE : c'est fragile et ce n'est pas la réponse attendue.

    Pour les cas où le nombre de colonnes ou de variables liées est inconnu à la compilation (générateur de requêtes, export générique), il existe le package DBMS_SQL, plus verbeux. Depuis 11g, on peut convertir un curseur DBMS_SQL en REF CURSOR (DBMS_SQL.TO_REFCURSOR) et inversement (DBMS_SQL.TO_CURSOR_NUMBER).

    Quiz

    Questions d'entretien

    Qu'est-ce qu'une transaction autonome ? Donne un cas d'usage légitime.

    Un sous-programme marqué PRAGMA AUTONOMOUS_TRANSACTION qui s'exécute dans une transaction indépendante de l'appelant : il doit se terminer par COMMIT ou ROLLBACK (sinon ORA-06519) et ne voit pas les modifications non validées de l'appelant. Cas légitime : journaliser une erreur ou un événement d'audit qui doit être conservé même si la transaction principale est annulée. Cas à éviter : contourner une table mutante ou faire du DML dans une fonction appelée en SQL.

    Différence entre TRUNCATE et DELETE ?

    DELETE est un DML : ligne par ligne, génère de l'undo, peut être annulé, déclenche les triggers, accepte un WHERE. TRUNCATE est un DDL : vide la table en réinitialisant ses segments, très rapide, commit implicite, pas de rollback, pas de trigger DML, pas de WHERE. Il échoue si une clé étrangère active référence la table (ORA-02266).

    Qu'est-ce qu'un deadlock et comment Oracle le traite-t-il ?

    Deux sessions qui attendent chacune un verrou tenu par l'autre. Oracle le détecte automatiquement : l'une des sessions reçoit ORA-00060, seul l'ordre en cours est annulé et c'est à l'application de faire ROLLBACK puis éventuellement de réessayer. Prévention : verrouiller dans un ordre constant, transactions courtes, FOR UPDATE NOWAIT ou WAIT n, index sur les clés étrangères. Rappel utile : en Oracle, les lectures ne posent pas de verrou et ne sont jamais bloquées.

    Comment te protèges-tu de l'injection SQL en PL/SQL ?

    D'abord, SQL statique dès que possible : chaque variable y est liée automatiquement. Ensuite, en dynamique, variables liées (USING) pour toutes les valeurs. Pour les identifiants qu'on ne peut pas lier, DBMS_ASSERT ou une liste blanche. Enfin, moindre privilège et vigilance sur le code en AUTHID DEFINER. Les variables liées améliorent aussi les performances en évitant un hard parse par valeur.

    Quand utiliser DBMS_SQL plutôt qu'EXECUTE IMMEDIATE ?

    Quand la structure de la requête est inconnue à la compilation : nombre de colonnes renvoyées ou nombre de variables liées variable (outil générique d'export, générateur de requêtes). Pour tout le reste, EXECUTE IMMEDIATE et OPEN FOR sont plus simples et plus lisibles.

    Chapitre 12 · 60 min

    Bonnes pratiques et optimisation

    La partie qui fait passer de « je sais écrire du PL/SQL » à « je sais livrer du PL/SQL en production ». En entretien, ces sujets sortent souvent sous la forme « raconte-moi comment tu as diagnostiqué un traitement lent ».

    • instrumenter un traitement pour le suivre en production ;
    • appliquer une démarche de diagnostic de performance et lire un plan d'exécution réel ;
    • citer des conventions de code, des règles de sécurité et les nouveautés récentes d'Oracle.

    Instrumenter son code

    DBMS_OUTPUT ne sert qu'en développement. Il écrit dans un tampon en mémoire de la session, que seul le client lit (SQL*Plus, SQL Developer) et seulement après la fin de l'appel : pendant un batch de deux heures, tu ne vois rien, et une application Java ou un job DBMS_SCHEDULER ne lit jamais ce tampon. Les vrais outils de production :

    Les valeurs sont visibles immédiatement par les autres sessions (pas besoin de COMMIT), et MODULE / ACTION sont repris dans les rapports AWR et ASH : le DBA peut dire quelle étape d'un batch consomme. Les chaînes sont courtes (48 octets pour le module, 32 pour l'action, 64 pour CLIENT_INFO). Pour une barre de progression avec estimation du temps restant, il existe aussi SET_SESSION_LONGOPS (vue V$SESSION_LONGOPS).

    • Table de log alimentée par une procédure en transaction autonome (niveau, message, horodatage, FORMAT_ERROR_BACKTRACE) : c'est le principe de log_erreur (chapitre 05, chapitre 11) et du package pkg_log de l'exercice 2. Le framework open source Logger en est un exemple répandu.
    • DBMS_SESSION.SET_IDENTIFIER pour retrouver l'utilisateur métier derrière un pool de connexions (colonne CLIENT_IDENTIFIER de V$SESSION).
    • UTL_CALL_STACK (12c) pour connaître le sous-programme appelant et enrichir les logs automatiquement.
    UTL_CALL_STACK : compter les profondeurs

    La profondeur 1 est le sous-programme en cours d'exécution (celui qui appelle UTL_CALL_STACK), la profondeur 2 son appelant, et ainsi de suite jusqu'à UTL_CALL_STACK.DYNAMIC_DEPTH. CONCATENATE_SUBPROGRAM(SUBPROGRAM(n)) renvoie un nom qualifié comme PKG_RH.AUGMENTER, ou __anonymous_block pour un bloc anonyme. Une profondeur supérieure à DYNAMIC_DEPTH lève une erreur.

    Laisser le compilateur t'aider

    La procédure est créée (un avertissement n'empêche pas la compilation : SQL*Plus affiche « created with compilation warnings »), et SHOW ERRORS liste, avec leur position LINE/COL, notamment ces deux avertissements :

    PLW-05018: unit P_TEST omitted optional AUTHID clause; default value DEFINER used PLW-06009: procedure "P_TEST" OTHERS handler does not end in RAISE or RAISE_APPLICATION_ERROR

    D'autres avertissements utiles : PLW-06002 (code inaccessible), PLW-07204 (conversion qui peut empêcher l'usage d'un index). En équipe, on peut transformer un avertissement en erreur bloquante : PLSQL_WARNINGS = 'ERROR:06009'. La compilation native (PLSQL_CODE_TYPE = NATIVE) accélère le code très calculatoire, pas le code qui passe son temps dans le SQL.

    Diagnostiquer un traitement lent

    Règle d'or : mesurer avant de corriger. On cherche d'abord où passe le temps, puis on traite la cause.

    Démarche de diagnostic : localiser le temps avant de choisir le remède.

    Le hint GATHER_PLAN_STATISTICS (ou STATISTICS_LEVEL = ALL dans la session) fait mesurer le nombre réel de lignes à chaque étape. Compare alors, ligne par ligne du plan :

    ColonneSignification
    StartsNombre de fois où l'étape a été exécutée (côté interne d'un NESTED LOOPS : une fois par ligne externe).
    E-RowsLignes estimées par l'optimiseur, par exécution de l'étape.
    A-RowsLignes réelles, cumulées sur toutes les exécutions.
    A-Time, BuffersTemps réel et blocs lus (cumulés, enfants compris).

    Un gros écart entre E-Rows × Starts et A-Rows signale une estimation fausse, souvent due à des statistiques absentes ou périmées (DBMS_STATS.GATHER_TABLE_STATS). L'optimiseur choisit alors un mauvais plan (boucles imbriquées au lieu d'une jointure par hachage, mauvais ordre de jointure). Pour le code PL/SQL lui-même, le profileur hiérarchique DBMS_HPROF donne le temps passé par sous-programme.

    Piège : DISPLAY_CURSOR montre le mauvais plan

    Sans sql_id, DISPLAY_CURSOR affiche le dernier ordre exécuté par la session. Avec SET SERVEROUTPUT ON, SQL*Plus appelle DBMS_OUTPUT.GET_LINES après chaque ordre : c'est ce plan-là que tu obtiens. Désactive SERVEROUTPUT ou passe le sql_id trouvé dans V$SQL. Autre piège : EXPLAIN PLAN donne un plan prévu, qui peut différer du plan réellement utilisé (variables liées, statistiques).

    Check-list performance à citer
    • Une requête ensembliste plutôt qu'une boucle (chapitre 09).
    • BULK COLLECT … LIMIT et FORALL quand la boucle est nécessaire.
    • Variables liées en SQL dynamique (chapitre 11) : moins de parsing, pas d'injection.
    • Pas de fonction sur une colonne indexée dans le WHERE (sinon index sur fonction).
    • Pas de conversion implicite sur une colonne indexée (WHERE code_varchar = 123).
    • COMMIT à la fin de l'unité de travail, pas à chaque ligne : chaque commit attend l'écriture du journal redo sur disque.
    • Fonctions appelées en SQL : jointure d'abord, sinon RESULT_CACHE ou PRAGMA UDF (chapitre 06).
    • PLS_INTEGER pour les compteurs, statistiques à jour sur les tables chargées par un batch.

    Pourquoi préfixer ? La colonne masque la variable

    Dans un ordre SQL, quand un nom peut désigner une colonne ou une variable PL/SQL, Oracle choisit la colonne. Avec une variable nom, DELETE FROM employes WHERE nom = nom; compare la colonne à elle-même : la condition est vraie pour toutes les lignes dont le nom n'est pas NULL, et la table est vidée. Le préfixe (p_nom, l_nom) ou la qualification par le nom du sous-programme (supprimer.nom) supprime l'ambiguïté.

    • Un sous-programme fait une chose, tient sur un écran, et a un nom en verbe (calculer_prime).
    • Types ancrés (%TYPE, %ROWTYPE) plutôt que tailles en dur.
    • Pas de valeurs en dur : constantes de package ou table de paramètres.
    • Pas de COMMIT dans les sous-programmes réutilisables : c'est l'appelant qui décide (chapitre 11).
    • Tests unitaires avec utPLSQL, code versionné dans Git, déploiement scripté (Liquibase, Flyway).

    Sécurité

    Le code PL/SQL s'exécute souvent avec les droits de son propriétaire : une faille se paie cher. Les règles à connaître :

    • Moindre privilège : le compte applicatif reçoit EXECUTE sur des packages, pas de droits directs sur les tables ni de droits DDL. Les packages deviennent la seule porte d'entrée vers les données.
    • AUTHID choisi consciemment (chapitre 06) : DEFINER (défaut) pour encapsuler l'accès aux tables, CURRENT_USER pour un utilitaire qui doit agir avec les droits de l'appelant. L'avertissement PLW-05018 vu plus haut rappelle de l'écrire explicitement.
    • ACCESSIBLE BY (12c) pour qu'un package interne ne soit appelable que par les unités listées.
    • SQL dynamique : variables liées et DBMS_ASSERT contre l'injection (chapitre 11).
    • Pas de données sensibles dans les logs : mots de passe, numéros de carte ou IBAN, données personnelles. Une table de journal est lue par beaucoup plus de monde que la table métier. Journalise des identifiants techniques (emp_id), pas les valeurs.
    • Messages d'erreur : le détail technique (SQLERRM, backtrace) va dans le journal ; l'utilisateur final reçoit un message fonctionnel.

    Exercice 3 · Diagnostiquer un plan d'exécution

    difficile

    En production, la table employes contient 2 millions de lignes et historique_salaires 8 millions (index idx_hist_emp sur emp_id). Un batch charge chaque nuit les nouvelles embauches (quelques dizaines par nuit), puis lance cette requête qui prend près de deux minutes :

    DISPLAY_CURSOR(format => 'ALLSTATS LAST') donne ce plan (simplifié, valeurs d'exemple) :

    | Id | Operation | Name | Starts | E-Rows | A-Rows | | 0 | SELECT STATEMENT | | 1 | | 180K | | 1 | NESTED LOOPS | | 1 | 4 | 180K | |* 2 | TABLE ACCESS FULL | EMPLOYES | 1 | 1 | 45000 | | 3 | TABLE ACCESS BY INDEX ROWID BATCHED | HISTORIQUE_SALAIRES | 45000 | 4 | 180K | |* 4 | INDEX RANGE SCAN | IDX_HIST_EMP | 45000 | 4 | 180K |
    1. Quelle ligne du plan montre une estimation fausse ? Justifie avec les colonnes.
    2. Quelle conséquence cette erreur a-t-elle eue sur le choix du plan ?
    3. Quelle est la cause la plus probable, vu le contexte du batch ? Comment corriger et vérifier ?
    4. Pourquoi ajouter un hint USE_HASH dans la requête n'est-il pas la bonne première réponse ?
    Voir la solution
    1. Ligne 2 : l'optimiseur attend 1 ligne (E-Rows) et en obtient 45 000 (A-Rows), avec Starts = 1. Les lignes 3 et 4, elles, sont justes : 4 lignes estimées par exécution × 45 000 exécutions = 180 000, ce que donne A-Rows. Ne pas comparer E-Rows et A-Rows sans tenir compte de Starts.
    2. Croyant n'avoir qu'un employé, l'optimiseur a choisi un NESTED LOOPS : l'index de l'historique est parcouru 45 000 fois (colonne Starts), avec autant d'accès aléatoires à la table. Pour ce volume, une jointure par hachage (HASH JOIN) sur un seul parcours de chaque table aurait en général été plus efficace.
    3. Des statistiques périmées : celles de employes datent de fin 2023. Les 45 000 embauches chargées depuis ne représentent qu'environ 2 % de la table, sous le seuil de 10 % de modifications au-delà duquel la tâche automatique de statistiques les recalcule. Pour l'optimiseur, la plus grande date_embauche connue est donc antérieure au 1er janvier 2024 : le prédicat est hors de la plage connue et il estime environ 1 ligne. Correction : appeler DBMS_STATS.GATHER_TABLE_STATS(USER, 'EMPLOYES') dans le batch, juste après le chargement. Vérification : relancer la requête et DISPLAY_CURSOR, constater que E-Rows est proche de 45 000 à la ligne 2 et que le plan est passé en HASH JOIN, et comparer A-Time.
    4. Le hint traite le symptôme dans une seule requête, fige le plan même quand les volumes changeront, et laisse les mêmes estimations fausses polluer toutes les autres requêtes sur employes. On corrige d'abord la cause (les statistiques) ; un hint ou une SQL Plan Baseline se discute ensuite, en dernier recours.
    En entretien

    Raconter ce raisonnement (« j'ai comparé E-Rows et A-Rows, trouvé l'étape où l'estimation décroche, remonté à la cause ») impressionne bien plus que réciter une liste de hints.

    Questions d'entretien

    Comment as-tu déjà optimisé un traitement PL/SQL ?

    Structure ta réponse : mesure (logs horodatés, DBMS_HPROF, AWR), cause (ex. boucle de 2 millions d'UPDATE unitaires avec COMMIT à chaque ligne), action (réécriture en MERGE ensembliste ou BULK COLLECT + FORALL, commit en fin de lot), résultat chiffré (« de 3 h à 6 min »). Un exemple concret vaut mieux qu'une liste théorique.

    Comment suis-tu un batch PL/SQL en production ?

    Pas avec DBMS_OUTPUT, qui n'est lu qu'à la fin et seulement par un client interactif. J'utilise DBMS_APPLICATION_INFO (module, action, avancement dans CLIENT_INFO) pour voir en direct où en est le traitement dans V$SESSION, et une table de log alimentée en transaction autonome (niveau, programme appelant via UTL_CALL_STACK, message, backtrace) pour garder une trace même si la transaction est annulée. Les horodatages du log permettent ensuite de savoir quelle étape a pris du temps.

    Une requête est lente : comment lis-tu son plan d'exécution ?

    Je récupère le plan réel avec GATHER_PLAN_STATISTICS et DBMS_XPLAN.DISPLAY_CURSOR(format => 'ALLSTATS LAST'), pas seulement EXPLAIN PLAN. Je cherche l'étape où A-Time et Buffers explosent, et celle où E-Rows × Starts s'écarte fortement de A-Rows. Un écart vient le plus souvent de statistiques absentes ou périmées, d'une fonction ou d'une conversion implicite sur une colonne, ou de colonnes corrélées. Je corrige la cause avant de penser aux hints.

    Comment tester du code PL/SQL ?

    Avec un framework de tests unitaires comme utPLSQL (annotations --%suite, --%test, assertions ut.expect), en isolant les données de test et en annulant les modifications après chaque test (utPLSQL fait un ROLLBACK vers un point de sauvegarde par défaut). Les tests tournent en intégration continue avec le déploiement des scripts.

    Trouve les bugs de prime_fin_annee

    entretien

    Cette procédure doit ajouter à la commission de chaque employé d'un département une prime de 10 % de son salaire, puis afficher le nom du département. Appelée avec 30, elle n'affiche rien et ne modifie rien. Explique pourquoi, liste tous les défauts (il y en a au moins six) et propose une version corrigée.

    Voir la solution

    Pourquoi rien ne se passe : dans un ordre SQL, la colonne dept_id masque le paramètre de même nom. WHERE dept_id = dept_id compare la colonne à elle-même : le SELECT INTO trouve les 4 départements et lève TOO_MANY_ROWS, que WHEN OTHERS THEN NULL avale. La procédure « réussit » sans rien faire.

    1. Paramètre nommé comme une colonne : le curseur aussi lit les 10 employés au lieu de ceux du département. Préfixer : p_dept_id (chapitre 12).
    2. WHEN OTHERS THEN NULL : masque toutes les erreurs. Traiter seulement NO_DATA_FOUND (département inexistant) et laisser remonter le reste (chapitre 05).
    3. EXIT WHEN en fin de boucle : après le dernier FETCH qui échoue, l_emp garde la ligne précédente, traitée une seconde fois. Ici l'effet est invisible (même calcul), mais un compteur ou un INSERT serait doublé (chapitre 04).
    4. Commission NULL : salaire * 0.1 + NULL vaut NULL, la prime des employés sans commission est perdue. Utiliser NVL(commission, 0) (chapitre 02).
    5. COMMIT dans la boucle : lent, valide un travail partiel en cas d'erreur, expose à ORA-01555 (fetch across commit) et retire la décision à l'appelant (chapitre 11).
    6. Ligne à ligne : un curseur et un UPDATE par employé là où un seul UPDATE suffit (chapitre 09).
    7. Bonus : le paramètre n'est pas ancré (employes.dept_id%TYPE) et le message ne dit pas combien d'employés ont été traités.
    4 prime(s) versée(s) : Ventes

    Pas de COMMIT : l'appelant valide. Avec 40, la procédure affiche 0 prime(s) versée(s) : RH ; avec 99, elle lève ORA-20011.

    • SAVE EXCEPTIONS isole les lignes en erreur. ERROR_INDEX est la position dans le FORALL : comme il parcourt 1 .. COUNT, c'est aussi l'indice dans l_ids. ERROR_CODE est positif, d'où le -p_code pour SQLERRM.
    • INDICES OF l_ids parce que l_ids devient creuse ; FORALL i IN 1 .. l_ids.COUNT lèverait ORA-22160. l_anc et l_nouv restent denses : on les lit avec les indices encore présents dans l_ids, qui correspondent toujours à la même ligne. Le FETCH suivant réinitialise les trois collections.
    • Le journal est en transaction autonome : son COMMIT ne valide que le journal, qui survit à un éventuel ROLLBACK de l'appelant. SQLERRM ne peut pas être appelé dans un ordre SQL : on passe par une variable.
    • Interactions avec le chapitre 10 : si le trigger trg_employes_audit_sal existe, l'insertion dans l'historique ferait doublon ; il faut choisir l'un ou l'autre. Si trg_sal_plafond rejette une ligne, elle arrive dans SQL%BULK_EXCEPTIONS avec ERROR_CODE = 20300. Seul le code est conservé : le texte passé à RAISE_APPLICATION_ERROR (« Salaire hors plafond… ») est perdu, et SQLERRM(-20300) ne renvoie qu'un message générique pour ce numéro. Pour garder le texte complet, la clause LOG ERRORS l'enregistre, elle.
    • Limites assumées : si une autre session supprime (et valide) un employé entre la lecture et l'UPDATE, celui-ci ne touche aucune ligne, sans erreur, puis l'insertion dans l'historique échoue sur la clé étrangère (ORA-02291) et fait échouer tout l'appel : il faudrait tester SQL%BULK_ROWCOUNT(i) avant de tracer ; pour se protéger des modifications concurrentes, on ajouterait FOR UPDATE au curseur, au prix d'un verrou sur toutes les lignes ciblées.
    • Alternative SQL pur, sans gestion fine des erreurs : un INSERT … SELECT dans l'historique puis un seul UPDATE avec la même expression, ou un UPDATE avec la clause LOG ERRORS INTO (table créée par DBMS_ERRLOG.CREATE_ERROR_LOG), qui joue en SQL un rôle proche de SAVE EXCEPTIONS. Sur un million de lignes, c'est souvent la solution la plus rapide : dis-le.
