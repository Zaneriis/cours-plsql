    Chapitre 01 · 45 min

    Architecture et bloc PL/SQL

    PL/SQL est le langage procédural d'Oracle : il ajoute variables, boucles, conditions et gestion d'erreurs autour du SQL, et il s'exécute dans le serveur de base de données, au plus près des données.

    • expliquer ce qui se passe entre le moteur PL/SQL et le moteur SQL ;
    • écrire un bloc avec ses quatre sections et des blocs imbriqués ;
    • distinguer bloc anonyme et unités stockées, et retrouver une erreur de compilation.

    Deux moteurs dans le serveur

    Quand tu envoies un bloc PL/SQL, le serveur Oracle le confie au moteur PL/SQL. Celui-ci exécute lui-même les instructions procédurales (affectations, IF, boucles) et passe chaque ordre SQL au moteur SQL. Chaque passage d'un moteur à l'autre est un changement de contexte : il a un coût. Toute la partie « performance » du cours (chapitre 09) consiste à en réduire le nombre.

    flowchart LR
  C["Client
    SQL Developer, appli Java…"] -- "1 seul appel réseau
    (le bloc entier)" --> P
  subgraph S["Serveur Oracle"]
    P["Moteur PL/SQL
    IF, boucles, variables"] -- "ordre SQL" --> Q["Moteur SQL
    SELECT, INSERT, UPDATE…"]
    Q -- "résultat" --> P
    Q --- D[("Données")]
  end
  P -- "résultat / erreur" --> C

    Un seul aller-retour réseau pour tout le bloc, mais un changement de contexte à chaque ordre SQL.

    En entretien : « Pourquoi utiliser PL/SQL plutôt que tout faire côté application ? »
    • Performance : un seul appel réseau au lieu de dizaines, et le code tourne à côté des données.
    • Sécurité : on donne EXECUTE sur une procédure sans donner l'accès direct aux tables.
    • Réutilisation et cohérence : la règle métier est écrite une fois, quel que soit le client (Java, Python, batch).
    • Intégration SQL : types identiques à ceux des colonnes, SQL statique vérifié à la compilation.

    Anatomie d'un bloc

    Tout code PL/SQL est organisé en blocs. Seule la section BEGIN … END est obligatoire.

  B --> E["EXCEPTION (optionnel)

    Blocs imbriqués et portée

    Un bloc peut contenir d'autres blocs, dans sa section exécutable ou dans sa section d'exception. Une variable est visible dans le bloc qui la déclare et dans ses sous-blocs. Si un sous-bloc redéclare le même nom, il masque la variable externe ; on peut encore l'atteindre en étiquetant le bloc externe.

    interne : 20, externe : 10 après : 10

    Un sous-bloc sert surtout à isoler une erreur : on traite l'exception localement et le traitement principal continue (voir chapitre 05).

    Questions d'entretien

    Quelle est la différence entre SQL et PL/SQL ?

    SQL est un langage déclaratif : on décrit le résultat voulu, une instruction à la fois. PL/SQL est un langage procédural qui encapsule du SQL dans des blocs avec variables, conditions, boucles et exceptions. PL/SQL est exécuté par le moteur PL/SQL du serveur ; le SQL qu'il contient est délégué au moteur SQL.

    Qu'est-ce qu'un bloc anonyme ? Quand l'utiliser ?

    Un bloc sans nom, non stocké, compilé à chaque exécution. On l'utilise pour des scripts ponctuels (migration de données, test, administration). Pour du code appelé régulièrement ou partagé, on crée une procédure, une fonction ou mieux un package.

    Que se passe-t-il quand on modifie une table utilisée par une procédure ?

    La procédure peut passer à l'état INVALID. Oracle la recompile automatiquement au prochain appel ; si la recompilation échoue (colonne supprimée par exemple), l'appel lève une erreur. On vérifie avec USER_OBJECTS.STATUS et on peut recompiler avec ALTER PROCEDURE … COMPILE ou DBMS_UTILITY.COMPILE_SCHEMA.

    NULL : la logique à trois valeurs

    NULL veut dire « inconnu ». Toute comparaison avec un inconnu donne un résultat inconnu, donc NULL, ni vrai ni faux. Un IF dont la condition vaut NULL se comporte comme si elle était fausse : on passe dans le ELSE.

    Piège

    IF l_a != l_b THEN ne détecte pas un changement de NULL vers une valeur. Pour comparer deux valeurs potentiellement nulles (dans un trigger d'audit par exemple), écris IF l_a != l_b OR (l_a IS NULL AND l_b IS NOT NULL) OR (l_a IS NOT NULL AND l_b IS NULL), ou utilise DECODE(l_a, l_b, 0, 1) = 1 qui traite deux NULL comme égaux.

    Conversions

    Oracle convertit implicitement les types quand il le peut, en s'appuyant sur les paramètres de session (NLS_DATE_FORMAT, NLS_NUMERIC_CHARACTERS). Un code qui marche sur ton poste peut donc échouer sur le serveur de production. Convertis toujours explicitement avec un masque.

    Piège

    WHERE date_embauche = '01/03/2015' fonctionne… tant que NLS_DATE_FORMAT vaut DD/MM/YYYY. Et WHERE TO_CHAR(id) = l_texte empêche l'utilisation de l'index sur id. Conversion implicite sur une colonne indexée = index ignoré.

    Erreurs de conversion fréquentes : ORA-06502: PL/SQL: numeric or value error (exception VALUE_ERROR, par exemple une chaîne trop longue pour la variable) et ORA-01722: invalid number (INVALID_NUMBER, levée dans un ordre SQL).

    Questions d'entretien

    Différence entre VARCHAR2 et CHAR ?

    CHAR(n) a une longueur fixe et complète avec des espaces ; VARCHAR2(n) stocke la longueur réelle. Avec CHAR, comparer à une variable VARCHAR2 peut échouer à cause des espaces de remplissage. On utilise VARCHAR2 sauf cas très particulier.

    Différence entre NVL et COALESCE ?

    NVL(a, b) prend exactement deux arguments et évalue toujours les deux. COALESCE(a, b, c…) accepte une liste, renvoie la première valeur non nulle et s'arrête dès qu'il la trouve (évaluation paresseuse). COALESCE est aussi standard SQL ANSI.

    Pourquoi PLS_INTEGER plutôt que NUMBER pour un compteur ?

    PLS_INTEGER utilise l'arithmétique native du processeur alors que NUMBER est une représentation décimale logicielle. Le gain est réel dans les boucles serrées. En contrepartie, la plage est limitée à ±2 147 483 647.

    Conditions

    Confirmé

    Deux CASE différents

    L'instruction CASE exécute des instructions et se termine par END CASE;. Si aucune branche ne correspond et qu'il n'y a pas de ELSE, elle lève CASE_NOT_FOUND (ORA-06592). L'expression CASE renvoie une valeur, se termine par END et renvoie NULL si rien ne correspond.

    Piège

    CASE l_x WHEN NULL THEN … ne fonctionne jamais : le CASE simple compare avec =. Pour tester NULL, utilise le CASE recherché : CASE WHEN l_x IS NULL THEN ….

    Les trois boucles

    BoucleQuandCondition testée
    LOOP … EXIT WHEN … END LOOPNombre d'itérations inconnu, au moins une exécution (lecture d'un curseur)Où tu places le EXIT
    WHILE cond LOOP … END LOOPNombre inconnu, éventuellement zéroAvant chaque itération
    FOR i IN a..b LOOP … END LOOPNombre connu à l'avanceBornes évaluées une seule fois

    Ce qu'il faut savoir sur FOR

    • L'indice est déclaré implicitement en PLS_INTEGER, n'existe que dans la boucle et est en lecture seule : j := 5 provoque PLS-00363.
    • Les bornes sont évaluées une seule fois à l'entrée : modifier la variable de borne dans la boucle ne change pas le nombre de tours.
    • Si la borne basse dépasse la borne haute (FOR i IN 5..1), la boucle ne s'exécute pas du tout. Pour descendre : REVERSE 1..5.
    • Le pas est toujours 1. Depuis 21c, on peut écrire FOR i IN 1..10 BY 2 ; avant, on multiplie l'indice.

    CONTINUE, EXIT et étiquettes

    CONTINUE (depuis 11g) passe à l'itération suivante ; EXIT sort de la boucle. Avec des boucles imbriquées, une étiquette permet de sortir de la boucle externe directement.

    1 2 4 3 6 9 4 8

    Un texte écrit avec DBMS_OUTPUT.PUT n'apparaît que lorsqu'un NEW_LINE (ou un PUT_LINE) termine la ligne : sans le NEW_LINE avant EXIT, « 4 8 » serait perdu.

    Astuce

    GOTO existe mais n'a quasiment jamais sa place : un recruteur verra son usage comme un signal négatif. Préfère EXIT, CONTINUE ou un sous-programme.

    Questions d'entretien

    Quelle différence entre EXIT et CONTINUE ?

    EXIT quitte la boucle (ou la boucle étiquetée) ; CONTINUE abandonne l'itération en cours et passe à la suivante. Les deux acceptent une forme conditionnelle EXIT WHEN / CONTINUE WHEN.

    Que fait une instruction CASE sans ELSE quand aucune branche ne correspond ?

    L'instruction CASE … END CASE lève CASE_NOT_FOUND (ORA-06592). L'expression CASE … END renvoie simplement NULL.

    SQL dans PL/SQL et curseurs

    Un curseur est une zone de travail où Oracle exécute une requête et garde sa position dans le résultat. Chaque ordre SQL de ton code en utilise un, que tu le déclares ou non.

    • utiliser SELECT INTO sans être surpris par ses deux exceptions ;
    • lire les attributs SQL%ROWCOUNT, %FOUND, %NOTFOUND, %ISOPEN ;
    • dérouler le cycle de vie d'un curseur explicite, puis le remplacer par une boucle FOR ;
    • verrouiller avec FOR UPDATE et renvoyer un résultat au client avec SYS_REFCURSOR.

    SELECT INTO : exactement une ligne

    SELECT … INTO est un curseur implicite qui doit ramener une et une seule ligne.

    Lignes trouvéesRésultat
    0Exception NO_DATA_FOUND (ORA-01403)
    1Les variables reçoivent les valeurs
    2 ou plusException TOO_MANY_ROWS (ORA-01422)
    Aucun employé dans le 40 Plusieurs employés dans le 20
    Piège classique d'entretien

    Une requête d'agrégat sans GROUP BY renvoie toujours une ligne. SELECT COUNT(*) INTO l_n FROM employes WHERE dept_id = 40 ne lève jamais NO_DATA_FOUND : l_n vaut 0. Et SELECT MAX(salaire) … sur zéro ligne donne NULL, sans exception.

    Astuce : tester l'existence

    Pour savoir si une ligne existe, ne fais pas COUNT(*) sur toute la table. Préfère SELECT COUNT(*) INTO l_n FROM employes WHERE emp_id = p_id AND ROWNUM = 1, ou mieux : tente directement l'action et traite l'exception.

    DML et curseur implicite

    Curseur explicite : le cycle de vie

    Pour parcourir plusieurs lignes, on déclare un curseur nommé. Son cycle de vie a quatre étapes : déclarer, ouvrir (la requête s'exécute et l'image des données est figée), lire ligne par ligne, fermer.

  Declare --> Ouvert : OPEN c
  Ouvert --> Ouvert : FETCH c INTO ... (%FOUND)

    Piège : où placer EXIT WHEN

    Le EXIT WHEN c%NOTFOUND doit suivre immédiatement le FETCH. Si tu le mets en fin de boucle, la dernière ligne est traitée deux fois : le FETCH qui échoue ne vide pas les variables, elles gardent la valeur précédente.

    La boucle FOR de curseur (à préférer)

    Elle fait OPEN, FETCH, test de fin et CLOSE pour toi, même si une exception interrompt la boucle. Depuis 10g, avec l'optimisation par défaut, elle lit même les lignes par paquets de 100 en interne.

    Dans un curseur, toute expression calculée doit avoir un alias (COUNT(e.emp_id) nb), sinon tu ne peux pas la lire depuis le record.

    Attributs d'un curseur explicite

    c%ISOPEN, c%FOUND, c%NOTFOUND et c%ROWCOUNT (nombre de lignes lues jusqu'ici, pas le total). Avant le premier FETCH, %FOUND et %NOTFOUND valent NULL.

    Verrouiller pour mettre à jour : FOR UPDATE

    FOR UPDATE pose un verrou sur les lignes sélectionnées dès l'OPEN, jusqu'au COMMIT ou ROLLBACK. WHERE CURRENT OF met ensuite à jour la ligne courante sans la rechercher.

    Variantes : WAIT n attend au plus n secondes ; SKIP LOCKED ignore les lignes déjà verrouillées (parfait pour une file de traitements partagée entre plusieurs sessions).

    Piège

    Un COMMIT à l'intérieur d'une boucle sur un curseur FOR UPDATE libère les verrous ; le FETCH suivant lève ORA-01002: fetch out of sequence.

    Un curseur classique est lié à une requête fixe. Une variable curseur (REF CURSOR) est un pointeur vers un curseur : on peut l'ouvrir sur des requêtes différentes et surtout le renvoyer au client (Java, .NET, Python), qui lira les lignes lui-même. SYS_REFCURSOR est un type faible prédéfini.

    Questions d'entretien

    Différence entre curseur implicite et explicite ?

    Le curseur implicite est créé et géré par Oracle pour chaque ordre SQL (SELECT INTO, DML) ; on lit ses attributs via SQL%. Le curseur explicite est déclaré par le développeur pour une requête multi-lignes, avec un contrôle complet du cycle OPEN / FETCH / CLOSE et des attributs nom%. La boucle FOR de curseur combine les deux avantages : curseur nommé ou en ligne, gestion automatique.

    Qu'est-ce qu'un REF CURSOR et à quoi sert-il ?

    Une variable qui pointe vers un curseur ouvert. Elle permet d'ouvrir des requêtes différentes à l'exécution (y compris dynamiques) et surtout de passer un jeu de résultats d'une procédure stockée à une application cliente sans tout charger en mémoire.

    À quoi servent FOR UPDATE et WHERE CURRENT OF ?

    FOR UPDATE verrouille les lignes à l'ouverture du curseur pour éviter qu'une autre session ne les modifie entre la lecture et la mise à jour (mise à jour perdue). WHERE CURRENT OF cible la ligne courante du curseur via son ROWID, sans nouvelle recherche.

    Que renvoie SQL%ROWCOUNT après un SELECT INTO réussi ?

    1. Après un SELECT INTO qui lève TOO_MANY_ROWS, il vaut aussi 1 (Oracle s'arrête à la deuxième ligne, qu'il ne compte pas comme lue).

    Chapitre 05 · 70 min

    Gestion des exceptions

    Tous les entretiens PL/SQL y passent. Il faut savoir lever, intercepter, transformer et journaliser une erreur, et surtout expliquer où elle va quand personne ne l'intercepte.

    • intercepter les exceptions prédéfinies et en déclarer de nouvelles ;
    • nommer une erreur Oracle avec PRAGMA EXCEPTION_INIT ;
    • lever une erreur métier avec RAISE_APPLICATION_ERROR ;
    • prédire la propagation d'une exception et ce qui est annulé.

    La section EXCEPTION

    Quand une erreur survient dans la section BEGIN, l'exécution saute immédiatement à la section EXCEPTION du même bloc. Oracle cherche le premier gestionnaire WHEN qui correspond ; WHEN OTHERS attrape tout ce qui reste et doit être le dernier.

    Trois façons de créer ses propres erreurs

    1. Exception utilisateur + RAISE

    Salaire sous le minimum : 1 / User-Defined Exception

    Pratique en interne, mais si elle sort du programme, l'appelant ne voit que ORA-06510: unhandled user-defined exception, sans message utile.

    2. RAISE_APPLICATION_ERROR : erreur métier avec message

    Lève une vraie erreur Oracle, avec un code entre -20000 et -20999 et un message (jusqu'à 2048 octets) que le client reçoit comme n'importe quelle ORA-. C'est la façon standard de signaler une règle métier violée à une application.

    ORA-20002: Augmentation de plus de 50 % refusée

    3. PRAGMA EXCEPTION_INIT : nommer une erreur Oracle

    Beaucoup d'erreurs Oracle n'ont pas de nom prédéfini. On leur en donne un pour les intercepter proprement plutôt que de tester SQLCODE dans WHEN OTHERS.

    Propagation : où va l'exception ?

    Si le bloc courant n'a pas de gestionnaire adapté, l'exception remonte au bloc englobant, puis à l'appelant, et ainsi de suite jusqu'au client. Trois règles à connaître par cœur :

    1. Une exception levée dans la section DECLARE (initialisation invalide) n'est pas traitée par la section EXCEPTION du même bloc : elle part directement au bloc englobant.
    2. Une exception levée dans un gestionnaire EXCEPTION part aussi directement au bloc englobant.
    3. Une fois l'exception traitée, l'exécution reprend après le bloc qui l'a traitée, jamais à la ligne qui l'a levée.

    En entretien : « Que devient la transaction si une exception n'est pas traitée ? »

    L'appel envoyé par le client (le bloc anonyme ou l'EXEC) est traité comme un seul ordre : si une exception remonte jusqu'au client, Oracle annule tout ce que cet appel a modifié (rollback au niveau instruction), mais pas le travail fait avant l'appel dans la même transaction. Si l'exception est traitée dans le code, rien n'est annulé automatiquement : les DML réussis avant l'erreur restent en attente de COMMIT ou ROLLBACK.

    Journaliser correctement une erreur

    SQLERRM donne le message, mais pas la ligne d'origine. DBMS_UTILITY.FORMAT_ERROR_BACKTRACE donne la pile des numéros de ligne jusqu'à l'endroit où l'erreur a été levée : indispensable en production.

    L'anti-pattern n°1 : WHEN OTHERS THEN NULL

    Avaler toutes les erreurs sans rien dire masque les bugs, laisse des données à moitié traitées et rend le diagnostic impossible. Le compilateur le signale d'ailleurs (avertissement PLW-06009). Règle : un WHEN OTHERS doit se terminer par RAISE ou RAISE_APPLICATION_ERROR, sauf cas très documenté (ex. traitement de masse qui journalise et continue).

    Astuce

    Pour continuer une boucle malgré une erreur sur une ligne, encapsule le traitement de la ligne dans un sous-bloc BEGIN … EXCEPTION … END; à l'intérieur de la boucle. L'erreur est traitée localement et la boucle reprend au tour suivant.

    Questions d'entretien

    Différence entre RAISE et RAISE_APPLICATION_ERROR ?

    RAISE lève une exception nommée (prédéfinie ou déclarée), ou re-lève l'exception courante quand il est utilisé seul dans un gestionnaire. RAISE_APPLICATION_ERROR crée une erreur Oracle avec un code entre -20000 et -20999 et un message personnalisé, que l'application cliente reçoit comme une erreur ORA- classique.

    Pourquoi WHEN OTHERS THEN NULL est-il dangereux ?

    Il masque toutes les erreurs, y compris celles qu'on n'avait pas prévues (espace disque, verrou, bug). Le programme semble réussir, la transaction peut être validée avec des données incohérentes et personne n'est prévenu. On doit au minimum journaliser puis re-lever.

    Comment retrouver la ligne qui a provoqué une erreur ?

    Avec DBMS_UTILITY.FORMAT_ERROR_BACKTRACE, appelé dans le gestionnaire d'exception. SQLERRM et FORMAT_ERROR_STACK donnent les messages, pas les lignes. Depuis 12c, UTL_CALL_STACK donne la même information de façon structurée.

    À quoi sert PRAGMA EXCEPTION_INIT ?

    À associer un nom d'exception déclaré à un numéro d'erreur Oracle qui n'a pas de nom prédéfini (par exemple -2292 pour une violation de clé étrangère), pour l'intercepter par son nom dans un gestionnaire dédié.

    Les paramètres OUT et IN OUT sont recopiés vers l'appelant seulement si le sous-programme se termine normalement. Si une exception non traitée en sort, la variable de l'appelant garde son ancienne valeur. Avec l'indication NOCOPY, le passage se fait par référence : plus rapide pour de grosses collections, mais la variable peut alors rester à moitié modifiée en cas d'erreur.

    Notations d'appel

    Astuce

    La notation nommée rend l'appel lisible et robuste : on peut ajouter un paramètre avec valeur par défaut à la fin d'une procédure sans casser les appels existants. En SQL*Plus, EXEC proc(...) est un raccourci pour BEGIN proc(...); END;.

    Fonctions appelées depuis SQL

    Pour être appelée depuis SQL, une fonction doit :

    • n'utiliser que des types SQL en paramètres et retour (pas de BOOLEAN avant 23ai, pas de record PL/SQL, pas de tableau associatif) ;
    • avoir uniquement des paramètres IN ;
    • ne pas faire de DML ni de COMMIT quand elle est appelée depuis un SELECT (sinon ORA-14551), sauf à être en transaction autonome ;
    • ne pas modifier la table interrogée par l'ordre qui l'appelle (sinon erreur de table mutante ORA-04091).

    Dans la requête ci-dessus, anciennete fait un SELECT pour chaque ligne, et elle est appelée deux fois par ligne. Chaque appel est un changement de contexte SQL → PL/SQL → SQL. Sur un million de lignes, c'est catastrophique : la logique doit être écrite en SQL pur (TRUNC(MONTHS_BETWEEN(SYSDATE, date_embauche)/12)) ou la fonction doit recevoir la date plutôt que l'identifiant.

    Questions d'entretien

    Peut-on faire un COMMIT dans une fonction ?

    Techniquement oui si elle est appelée depuis PL/SQL, mais c'est une mauvaise pratique : une fonction calcule, elle ne doit pas avoir d'effet de bord. Appelée depuis un SELECT, un DML ou un COMMIT lève ORA-14551 (sauf transaction autonome, réservée à des cas comme la journalisation).

    Qu'est-ce que NOCOPY ?

    Une indication au compilateur pour passer un paramètre OUT ou IN OUT par référence au lieu de par copie. Utile pour les grosses collections ou les LOB. C'est une indication, pas une garantie, et en cas d'exception les modifications partielles sont visibles chez l'appelant.

    Différence entre DETERMINISTIC et RESULT_CACHE ?

    DETERMINISTIC est une promesse faite à l'optimiseur que la fonction renvoie toujours la même chose pour les mêmes entrées ; le bénéfice est limité à la requête en cours et c'est requis pour un index sur fonction. RESULT_CACHE stocke réellement les résultats en mémoire partagée entre sessions et les invalide quand les tables sources changent.

    Une procédure peut-elle renvoyer une valeur ?

    Pas avec RETURN valeur (un RETURN; seul y sert à sortir immédiatement). Elle renvoie des valeurs via des paramètres OUT / IN OUT, ou un SYS_REFCURSOR en OUT pour un jeu de résultats.

    PerformanceLe package entier est chargé en mémoire au premier appel ; les appels suivants n'ont pas à recharger chaque unité.
    État de sessionLes variables de package conservent leur valeur entre les appels, pendant toute la session.
    SurchargePlusieurs sous-programmes de même nom avec des paramètres différents (en nombre, ordre ou famille de types).
    SécuritéUn seul GRANT EXECUTE ON pkg_rh donne accès à toute l'API, sans accès direct aux tables.

    L'état de package et ORA-04068

    Chaque session a sa propre copie des variables de package : deux utilisateurs ne partagent jamais g_nb_appels. Si un package possède des variables (il a un « état ») et qu'on recompile son corps pendant que des sessions l'utilisent, ces sessions reçoivent au prochain appel :

    ORA-04068: existing state of packages has been discarded ORA-04061: existing state of package body "RH.PKG_RH" has been invalidated

    Le second appel fonctionne, car l'état a été réinitialisé. Les remèdes : éviter les variables globales quand ce n'est pas nécessaire (un package sans état n'a pas ce problème), déplacer les constantes littérales… ou utiliser le Edition-Based Redefinition pour les déploiements sans interruption.

    Piège

    Une variable de package n'est pas partagée entre sessions et n'est pas transactionnelle : un ROLLBACK ne remet pas g_nb_appels à sa valeur précédente. Avec un pool de connexions côté application, une variable de package peut « fuiter » d'un utilisateur web à l'autre qui réutilise la même session.

    Astuce

    Les mots-clés ACCESSIBLE BY (pkg_api) (12c) limitent les unités autorisées à appeler un package : utile pour un package « interne » qui ne doit être appelé que par la couche API.

    Questions d'entretien

    Peut-on avoir une spécification sans corps ?

    Oui, si elle ne déclare que des éléments sans implémentation : constantes, types, exceptions, variables. C'est courant pour un package de constantes ou de types partagés. Le corps devient obligatoire dès qu'on déclare un sous-programme ou un curseur avec requête cachée.

    Si je modifie le corps d'un package, les procédures qui l'appellent deviennent-elles invalides ?

    Non. Elles dépendent de la spécification. Seule une modification de la spécification invalide les appelants. C'est un des principaux arguments en faveur des packages.

    Quelles sont les règles de la surcharge ?

    Les versions doivent différer par le nombre, l'ordre ou la famille de types des paramètres. Différer uniquement par le mode (IN/OUT), par le nom du paramètre, par le type de retour, ou par des sous-types de la même famille (NUMBER / INTEGER) provoque une erreur d'appel ambigu (PLS-00307). On peut surcharger des sous-programmes de package ou locaux, pas des procédures autonomes.

    Qu'est-ce que SERIALLY_REUSABLE ?

    Un PRAGMA qui limite la durée de vie de l'état d'un package à un seul appel serveur au lieu de toute la session. Il économise de la mémoire dans les systèmes avec beaucoup de sessions, mais le package ne peut alors pas être utilisé depuis SQL ni depuis un trigger.

    Quelles sont les différences entre les trois types de collections ?

    Le tableau associatif est purement PL/SQL, sans initialisation, indexé par entier ou chaîne, creux possible. La table imbriquée doit être initialisée, peut devenir creuse et peut être un type SQL (colonne, TABLE(), MULTISET).     Différence entre COUNT et LAST ?

    Chapitre 09 · 70 min

    Performance : BULK COLLECT et FORALL

    Le sujet qui distingue un développeur PL/SQL confirmé. Dès que tu traites des milliers de lignes, la question n'est plus « est-ce que ça marche » mais « combien d'allers-retours entre les moteurs ».

    • expliquer le coût d'un changement de contexte avec un exemple chiffré ;
    • charger des lignes par lots avec BULK COLLECT … LIMIT ;
    • écrire en masse avec FORALL et gérer les erreurs ligne par ligne avec SAVE EXCEPTIONS ;
    • savoir quand le SQL pur bat tout le reste.

    Le problème : ligne par ligne, lent par lent

    Une boucle qui exécute un INSERT à chaque tour fait deux changements de contexte par ligne (PL/SQL vers SQL, puis retour). FORALL envoie toutes les lignes au moteur SQL en un seul aller-retour. Lance la course :

    Sur 100 000 lignes, l'écart typique est d'un facteur 10 à 50. Tom Kyte, l'une des références d'Oracle, résume l'ordre de préférence ainsi :

    1. Fais-le en un seul ordre SQL si c'est possible (INSERT … SELECT, MERGE, UPDATE avec sous-requête).
    2. Sinon, fais-le en PL/SQL par lots (BULK COLLECT + FORALL).
    3. Ligne par ligne seulement quand il n'y a pas d'autre choix.

    BULK COLLECT : lire en masse

    Piège

    BULK COLLECT ne lève jamais NO_DATA_FOUND : sans ligne, la collection est simplement vide (COUNT = 0). Et sans LIMIT, une table de 50 millions de lignes est chargée entièrement en mémoire de session (PGA).

    Le schéma standard avec LIMIT

    Piège d'entretien : EXIT WHEN c%NOTFOUND

    Si le dernier lot contient moins de lignes que LIMIT (par exemple 350 sur 1 000), c%NOTFOUND est déjà TRUE après ce FETCH. Avec EXIT WHEN c%NOTFOUND juste après le FETCH, ces 350 lignes ne sont jamais traitées. Soit on teste COUNT = 0 juste après le FETCH, soit on met EXIT WHEN c%NOTFOUND à la fin de la boucle.

    FORALL : écrire en masse

    FORALL n'est pas une boucle : c'est un seul ordre DML exécuté avec un tableau de valeurs liées. Il ne peut contenir qu'un seul ordre INSERT, UPDATE, DELETE ou MERGE.

    Total : 9 Dept 20 : 5 ligne(s) Dept 30 : 4 ligne(s) Dept 40 : 0 ligne(s)

    Pour une collection creuse, FORALL i IN 1 .. n échoue. On utilise FORALL i IN INDICES OF l_coll (parcourt les indices existants) ou VALUES OF l_index (parcourt les indices listés dans une autre collection).

    SAVE EXCEPTIONS : ne pas tout perdre pour une ligne

    Par défaut, la première erreur arrête le FORALL (les lignes déjà traitées restent faites, pas les suivantes). Avec SAVE EXCEPTIONS, Oracle traite toutes les lignes, mémorise les échecs, puis lève ORA-24381 à la fin. On lit le détail dans SQL%BULK_EXCEPTIONS.

    3 lignes mises à jour, 2 en erreur emp 103 : ORA-02290: check constraint (.) violated emp 109 : ORA-02290: check constraint (.) violated

    Fonctions pipelined

    Une fonction « table » renvoie une collection qu'on interroge avec TABLE(). En mode PIPELINED, elle envoie chaque ligne dès qu'elle est prête (PIPE ROW) au lieu de construire toute la collection en mémoire : idéal pour des transformations de données en flux (ETL).

    Quiz

    Questions d'entretien

    Qu'est-ce qu'un changement de contexte et comment le réduire ?

    Le passage du moteur PL/SQL au moteur SQL (et retour) à chaque ordre SQL exécuté depuis PL/SQL, ou à chaque appel de fonction PL/SQL depuis SQL. On le réduit en écrivant un seul ordre SQL ensembliste, en utilisant BULK COLLECT et FORALL, et en évitant les fonctions PL/SQL appelées ligne à ligne dans les requêtes.

    Pourquoi utiliser LIMIT avec BULK COLLECT ?

    Pour borner la mémoire de session : sans LIMIT, tout le résultat est chargé dans la PGA. Une valeur de 100 à 1 000 donne l'essentiel du gain de performance sans risque mémoire.

    FORALL est-il une boucle ?

    Non. C'est une instruction qui envoie un seul ordre DML au moteur SQL avec un tableau de valeurs liées. Il ne peut contenir qu'un seul DML, pas de logique procédurale.

    Que se passe-t-il quand une ligne échoue dans un FORALL sans SAVE EXCEPTIONS ?

    Le FORALL s'arrête à cette ligne et lève l'exception. Les lignes traitées avant restent modifiées (rollback au niveau de l'instruction seulement pour la ligne fautive) tant que l'appelant ne fait pas de ROLLBACK. Les lignes suivantes ne sont pas traitées.

    Il existe aussi des triggers système : sur événements DDL (BEFORE DROP ON SCHEMA), ou base (AFTER LOGON ON DATABASE, AFTER SERVERERROR).

    La table mutante (ORA-04091)

    Un trigger de ligne ne peut pas lire ni modifier la table sur laquelle il est en train de se déclencher : elle est « en mutation », son contenu est incohérent au milieu de l'ordre DML.

    ORA-04091: table RH.EMPLOYES is mutating, trigger/function may not see it ORA-06512: at "RH.TRG_SAL_PLAFOND", line 4

    La solution moderne (11g+) est le trigger composé : on mémorise les lignes concernées dans la section de ligne, et on fait le contrôle dans la section AFTER STATEMENT, où la table est de nouveau lisible.

    Autres solutions à citer

    Avant 11g : un package avec une collection, un trigger de ligne qui la remplit et un trigger d'instruction qui la traite. Souvent, la meilleure réponse est de sortir la règle du trigger : la mettre dans la procédure d'API qui fait la mise à jour, ou dans une contrainte déclarative quand c'est possible.

    Bonnes pratiques

    • Pas de COMMIT ni ROLLBACK dans un trigger (ORA-04092), sauf transaction autonome réservée au log.
    • Garde les triggers courts : appelle une procédure de package plutôt que d'écrire 200 lignes dedans.
    • Préfère une contrainte (CHECK, FOREIGN KEY, UNIQUE) à un trigger quand elle suffit : plus rapide, plus fiable, visible.
    • Évite la logique métier « cachée » en cascade de triggers : difficile à déboguer, à tester et à faire évoluer.
    • Si plusieurs triggers du même type existent, impose l'ordre avec FOLLOWS / PRECEDES (11g).
    • Désactiver temporairement : ALTER TRIGGER … DISABLE ou ALTER TABLE … DISABLE ALL TRIGGERS (chargements massifs).

    Questions d'entretien

    Qu'est-ce qu'une table mutante et comment l'éviter ?

    Une table en cours de modification par l'ordre DML qui a déclenché un trigger de ligne. Le trigger ne peut pas la lire ni la modifier : ORA-04091. Solutions : trigger composé (stocker en section ligne, traiter en AFTER STATEMENT), trigger d'instruction, ou déplacer la règle hors du trigger.

    Peut-on modifier :NEW dans un trigger AFTER ?

    Dans quel ordre se déclenchent les triggers ?

    Chapitre 11 · 65 min

    Transactions et SQL dynamique

    Deux sujets qui touchent à la robustesse : qui décide de valider, comment journaliser une erreur qui sera annulée, et comment construire du SQL à l'exécution sans ouvrir une faille de sécurité.

    • maîtriser COMMIT, ROLLBACK, SAVEPOINT et savoir qui doit valider ;
    • utiliser une transaction autonome pour la journalisation ;
    • écrire du SQL dynamique avec EXECUTE IMMEDIATE et des variables liées ;
    • expliquer et empêcher une injection SQL.

    Transactions

    Une transaction commence au premier ordre DML et se termine par COMMIT (validation) ou ROLLBACK (annulation). Les ordres DDL (CREATE, ALTER, DROP, TRUNCATE) font un COMMIT implicite avant et après eux. Tant qu'une transaction n'est pas validée, les autres sessions voient les anciennes valeurs (lecture cohérente) et les lignes modifiées sont verrouillées.

    En entretien : « Qui doit faire le COMMIT ? »

    L'appelant de plus haut niveau, celui qui connaît le périmètre de l'unité de travail (le service applicatif, le job batch). Une procédure réutilisable ne doit pas valider elle-même : si elle est appelée au milieu d'un traitement plus large, son COMMIT validerait aussi le travail de l'appelant, qui ne pourrait plus tout annuler.

    Transactions autonomes

    PRAGMA AUTONOMOUS_TRANSACTION fait tourner un sous-programme dans une transaction indépendante : il peut valider sans valider le travail de l'appelant, et un ROLLBACK de l'appelant n'annule pas ce qu'il a validé.

    sequenceDiagram
  participant T as Transaction principale
  participant A as log_erreur (autonome)
  T->>T: UPDATE employes (non validé)
  T->>T: erreur !
  T->>A: appel log_erreur
  Note over A: transaction séparée
  A->>A: INSERT journal_erreurs
  A->>A: COMMIT (valide seulement le journal)
  A-->>T: retour
  T->>T: ROLLBACK (annule l'UPDATE)
  Note over T,A: le journal reste, l'UPDATE est annulé
    Pièges
    • Un sous-programme autonome doit se terminer par COMMIT ou ROLLBACK, sinon ORA-06519: active autonomous transaction detected and rolled back.
    • Il ne voit pas les modifications non validées de l'appelant. S'il essaie de modifier une ligne verrouillée par l'appelant : interblocage avec lui-même (ORA-00060).
    • Ce n'est pas un moyen de contourner la table mutante ou de faire du DML dans une fonction appelée en SQL : réserve-le au journal et à l'audit.

    SQL dynamique : EXECUTE IMMEDIATE

    Le SQL statique est vérifié à la compilation. Quand la requête n'est connue qu'à l'exécution (nom de table variable, filtres optionnels, DDL), on construit une chaîne et on l'exécute.

    Pourquoi des variables liées ?
    • Sécurité : la valeur n'est jamais interprétée comme du SQL, donc pas d'injection.
    • Performance : WHERE emp_id = :id est analysé une fois et réutilisé ; WHERE emp_id = 104, = 105… provoquent une analyse complète (hard parse) à chaque valeur et saturent le cache partagé.

    En SQL statique dans PL/SQL, chaque variable est automatiquement une variable liée : c'est un avantage gratuit du statique.

    L'injection SQL

    La chaîne exécutée devient … WHERE poste = 'x' OR '1'='1'. Sur une requête qui renvoie des données, un attaquant peut ajouter un UNION SELECT sur une autre table. Les défenses :

    1. Préférer le SQL statique quand c'est possible (ici, il suffit !).
    2. Sinon, variables liées pour toute valeur : … WHERE poste = :p' INTO l_nb USING p_poste.
    3. Pour un identifiant (table, colonne) qui ne peut pas être lié : valider avec DBMS_ASSERT (SIMPLE_SQL_NAME, SQL_OBJECT_NAME, ENQUOTE_NAME) ou une liste blanche.
    4. Principe du moindre privilège : AUTHID adapté, compte applicatif sans droits DDL.

    Pour les cas où le nombre de colonnes ou de variables liées est inconnu à la compilation (générateur de requêtes), il existe le package DBMS_SQL, plus verbeux. Depuis 11g, on peut convertir un curseur DBMS_SQL en REF CURSOR et inversement.

    Questions d'entretien

    Qu'est-ce qu'une transaction autonome ? Donne un cas d'usage légitime.

    Un sous-programme marqué PRAGMA AUTONOMOUS_TRANSACTION qui s'exécute dans une transaction indépendante de l'appelant. Cas légitime : journaliser une erreur ou un événement d'audit qui doit être conservé même si la transaction principale est annulée.

    Différence entre TRUNCATE et DELETE ?

    DELETE est un DML : ligne par ligne, génère de l'undo, peut être annulé, déclenche les triggers, accepte un WHERE. TRUNCATE est un DDL : vide la table en réinitialisant ses segments, très rapide, commit implicite, pas de rollback, pas de trigger DML, pas de WHERE. Il échoue si une clé étrangère active référence la table.

    Quand utiliser DBMS_SQL plutôt qu'EXECUTE IMMEDIATE ?

    Quand la structure de la requête est inconnue à la compilation : nombre de colonnes renvoyées ou nombre de variables liées variable (outil générique d'export, générateur de requêtes). Pour tout le reste, EXECUTE IMMEDIATE et OPEN FOR sont plus simples et plus rapides.

    Bonnes pratiques et optimisation

    La partie qui fait passer de « je sais écrire du PL/SQL » à « je sais livrer du PL/SQL en production ». En entretien, ces sujets sortent souvent sous la forme « raconte-moi comment tu as diagnostiqué un traitement lent ».

    Instrumenter son code

    DBMS_OUTPUT ne sert qu'en développement : rien ne s'affiche avant la fin du bloc et personne ne le lit en production. Les vrais outils :

    • Table de log alimentée par une procédure autonome (niveau, message, horodatage, FORMAT_ERROR_BACKTRACE). Le framework open source Logger en est un exemple répandu.
    • DBMS_SESSION.SET_IDENTIFIER pour retrouver l'utilisateur métier derrière un pool de connexions.
    • UTL_CALL_STACK (12c) pour connaître le sous-programme appelant, par exemple pour enrichir les logs.

    Laisser le compilateur t'aider

    D'autres avertissements utiles : PLW-06002 (code inaccessible), PLW-07204 (conversion qui empêche un index). La compilation native (PLSQL_CODE_TYPE = NATIVE) accélère le code très calculatoire, pas le code qui fait surtout du SQL.

    Diagnostiquer un traitement lent

    flowchart TD

    Compare les colonnes E-Rows (estimé) et A-Rows (réel) : un gros écart signale des statistiques absentes ou fausses (DBMS_STATS.GATHER_TABLE_STATS). Pour le PL/SQL, le profileur hiérarchique DBMS_HPROF donne le temps passé par sous-programme.

    Check-list performance à citer
    • Une requête ensembliste plutôt qu'une boucle.
    • BULK COLLECT … LIMIT et FORALL quand la boucle est nécessaire.
    • Variables liées en SQL dynamique.
    • Pas de fonction sur une colonne indexée dans le WHERE (sinon index sur fonction).
    • Pas de conversion implicite sur une colonne indexée.
    • COMMIT à la fin de l'unité de travail, pas à chaque ligne (chaque commit force une écriture du journal redo).
    • PLS_INTEGER pour les compteurs, cache de résultats pour les lectures répétées.

    Sans préfixe, une variable qui porte le nom d'une colonne est masquée par la colonne dans un ordre SQL. DELETE FROM employes WHERE nom = nom; avec une variable nom compare la colonne à elle-même… et supprime toute la table (sauf les noms NULL).

    Gestion des augmentations annuelles

    entretien

    Écris un package pkg_augmentations avec une procédure publique appliquer(p_annee IN PLS_INTEGER, p_nb_ok OUT PLS_INTEGER, p_nb_ko OUT PLS_INTEGER) :

    1. Taux : 3 % pour les employés de 5 ans d'ancienneté ou plus, 2 % sinon, 0 % pour les stagiaires.
    2. Une augmentation ne peut pas faire dépasser 10 000 : l'employé est alors plafonné à 10 000.
    3. Chaque modification est tracée dans historique_salaires.
    4. Un employé en erreur ne doit pas bloquer les autres : l'erreur est journalisée (transaction autonome) et comptée.
    5. Le traitement doit être performant pour 1 million d'employés.
    6. Pas de COMMIT dans le package : l'appelant décide.

    Avant d'ouvrir la solution : écris la spécification, puis le corps. Réfléchis à l'option SQL pur et à l'option FORALL … SAVE EXCEPTIONS.

    Voir une solution

    Points à commenter devant le recruteur :

    • Les stagiaires (0 %) sont exclus dès la requête : inutile de les mettre à jour.
    • Le calcul est fait en SQL dans le curseur, les écritures en FORALL par lots de 1 000 : mémoire bornée, peu de changements de contexte.
    • SAVE EXCEPTIONS isole les lignes en erreur ; le journal est en transaction autonome pour survivre à un éventuel ROLLBACK de l'appelant.
    • INDICES OF parce que la collection devient creuse après suppression des lignes en erreur.
    • Si le trigger d'audit du chapitre 10 existe, l'insertion dans l'historique ferait doublon : il faut choisir l'un ou l'autre.
    • Alternative sans gestion fine des erreurs : un seul UPDATE + un INSERT … SELECT dans l'historique, ou un UPDATE avec la clause LOG ERRORS INTO (table créée par DBMS_ERRLOG), qui fait le même travail que SAVE EXCEPTIONS en SQL pur.
